# software-design

设计阶段在设计的是**决定**，不是组件清单：责任怎么分、边界在哪、接口承诺什么、为什么这样而不是那样、怎么证明它满足要求。IEEE 1016 定义设计为"a conceptualization of a design subject"，必须"demonstrates a means of fulfilling requirements, supports analysis and evaluation"；Kruchten 压缩为 `Architecture = {Elements, Forms, Rationale/Constraints}`。三者缺一就是笔记，不是设计。

本 skill 用步骤 0–7 引导思考与验证：后续决定必须能追溯到前面的需求与理由，走查或评估发现问题时回到相应步骤修正。步骤不是文件划分，也不是逐项照搬的章节模板。各步骤的「写清」列出文档要有的内容，放进哪份文档、放在正文还是附件，由「文档形态」决定。文中的「阶段」指设计、实现等工作阶段，不指这里的步骤。

## 贯穿全程的规则

- **文档陈述当前设计。** 文档（正文与附件）写当前成立的设计，不是草稿或工作记录：不标草稿 / 评审中 / 已定之类的状态，不分草稿区和定稿区，不并列新旧规则，不写变更历史，历史由 git 保留。
- **正文不留实验痕迹。** 实验、原型、微基准、model checking 是得出结论的手段。正文只写得出的结论，以域性质、约束、决定或理由的形式出现；结论需要的观测证据（测量值及其条件）作为设计参考放进附件，结论旁链接到对应条目。实验的计划、过程、迭代和"试过 X"的叙述是工作记录，按上一条不进文档。
- **未定项目当场关闭。** 任何一步发现未定项目都立即决定，不在文档里留"待确认""待定"或以后再做的关闭事件。关闭它的动作就是当下要做的事：能靠取证、实验或原型确定的立即去做，需要用户取舍的立即询问用户，结论写进文档并修正受影响的步骤。只有用户明确交代留到下一阶段的项目可以保留，文档在该项所在位置写明这一交代和它留到的阶段。

## 总体

|步骤|回答的问题|需要写清的内容|验证|
|---|---|---|---|
|0 定位|这份文档描述哪一层的哪个元素、给谁、决定什么、不决定什么、承接什么|标题、层级与元素、读者与审批者、要决定的事、设计边界（含非目标）、输入衔接|读者能一句话复述要决定的事及它在哪一层，并说出边界外的事归谁|
|1 问题域|世界里有什么、它们固有性质是什么、机器与它们共享什么现象、要求是什么|域清单、共享现象表、需求（现有 / 新增 / 推出）|每条域性质有证据；需求可追溯到来源|
|2 驱动|哪些质量属性和约束塑造架构|质量场景（六要素）、约束、优先级|每个场景有 response measure，可被证伪|
|3 模型|少数核心抽象及其关系；每个抽象隐藏什么决定|概念模型、不变量、抽象间的允许/禁止关系|模型能把 1 的每条需求和 2 的每个场景走通|
|4 结构|下一层元素、责任、契约、视图|下一层元素指南（含输出衔接）、接口规格、依赖关系、部署/进程视图|每个元素能指到 3 的抽象；每个接口有语义、错误、undesired events|
|5 走查|关键场景、失败路径、状态转换在 4 上走得通吗|逐场景 trace、崩溃矩阵|卡点归零（回 3/4 修正）|
|6 评估|风险、敏感点、权衡、替代方案|替代方案对比、risks / sensitivity / tradeoff points、证伪条件|每个重要决定有可信替代与理由；没有未定项目（用户明确交代留到下一阶段的除外）|
|7 维护|设计变化后，哪些内容仍有效，哪些应改写、合并或删除|当前决定、理由、后果及重审条件|文档树对应当前分解；没有失效篇章、重复文件或悬空引用|

步骤 1–3 是"想清楚"，4–5 是"画出来并证明"，6–7 是"让别人能拒绝并让未来能改"。跳过 1–3 直接写 4 是最常见的失败：产出组件清单、类型草图、约束列表，全部看起来像设计但没有一条能被反驳。

每一层文档都走这些步骤，但输入不同：系统上下文文档从真实世界的域与需求出发；下层文档的问题域与驱动是上级分配给该元素的需求、契约与质量场景（即它的输入衔接），加上该元素自身直接面对的域性质（它读写的外部系统、存储、时钟），不重抄上级的全局论证。

## 步骤 0 定位

**注重**：这份文档在 C4 哪一层描述哪个元素、给谁、决定什么、不决定什么、从上级承接什么。

**写清**：标题；层级与元素；上级文档链接；读者与审批者；一段话说明要决定的事；设计边界：本文档决定什么，不决定的事分别归上级、下级、同级文档，还是非目标（Google："plausible objectives intentionally not pursued"）；输入衔接：从上级承接的需求、契约、质量场景与约束，逐项链接到上级给出它的章节。系统上下文文档没有上级，它的输入是步骤 1 的需求来源与域证据。边界与衔接的规则见「文档形态」。

**走偏**：没有非目标，范围随对话漂移；边界只写做什么，不写不决定的事归谁，讨论一深入就替上级或下级做决定；输入只链接到上级文档整体，看不出承接的是哪条需求或契约；没有审批者，文档"存在即通过"。

## 步骤 1 问题域

方法：Jackson 问题分析——先域后机器。

**注重**：
- 域：世界里独立存在的东西（用户、外部系统、物理对象、数据）。每个域写它**固有的、我们不能设计的性质**：它是什么的真相来源、它的能力是否部分、它会怎么失败、它的时钟和身份规则。
- 机器：要建的系统。只写它与各域**共享的现象**（事件、命令、观察、数据），这是设计在机器与世界之间唯一能约束的东西。
- 需求：期望在**问题域**里成立的性质，不是机器的功能列表。分三组：现有行为（从现有系统的真实入口取证）、新增（来源原文）、从域性质**推出**的必然需求（例：外部系统结果有"未知"这一种 ⇒ 必须有未知收敛路径）。
- 设计义务：`机器规格 + 域性质 ⇒ 需求`。后面每一步都要能回到这条。

**写清**：域清单（每条性质附证据：源码行号、官方文档、原文引用）；共享现象表（域 → 机器 / 机器 → 域）；需求编号。

**验证**：每条域性质能指到证据；现有行为按真实入口（路由、CLI、协议）逐条列全，不按总结报告转述；新增需求有来源原文。

**走偏**：
- 从解决方案反推问题（先有组件再找它解决什么）。
- 把现有实现的结构当成域性质（"账户有一个 broker 连接"是实现，"账户对同一 venue 的写必须串行"才是域性质）。
- 用调查报告代替源码：报告是对源码的转述，会丢细节和出错；现有行为直接看入口。
- 把新系统要支持的场景当成已有事实，或反过来把现有行为当成必须保留的契约。

## 步骤 2 驱动

方法：QAW 场景 + ADD 的架构驱动。

**注重**：把质量形容词变成可证伪的场景；把约束和质量分开；定优先级。

**写清**：
- 质量场景表，每条六要素：stimulus source / stimulus / artifact / environment / response / **response measure**。"快""可靠""可扩展"不是场景；"200 条上游 WS 各 125 msg/s 持续 10 分钟，p99 处理延迟 ≤ X，零丢失，队列有界"才是。
- 约束表：来源（业务 / 技术 / 组织）、内容、它排除了什么。
- 优先级：按业务重要性 × 架构风险（ATAM utility tree 的两维）。
- 功能需求里**架构显著**的那几条（改变结构的），其余留给步骤 4。

**验证**：每条场景能回答"如果做出来不满足，怎么观测到"；约束是真约束不是偏好。

**走偏**：
- 只有形容词；benchmark 数字当 SLO（localhost 合成测量 ≠ 产品预算）。
- 把偏好写成约束（"用 X 语言"若说不出来源和它排除了什么，就是偏好）。
- 忘记负载形状：吞吐、并发、数据体积、突发。

## 步骤 3 模型

方法：Parnas 信息隐藏 + Brooks 概念完整性 + DDD 有界上下文。

**注重**：
- 找出**难的或会变的决定**，每个藏进一个抽象。这是分解的准则，不是按执行步骤或数据形状分。
- 抽象要少，彼此关系要清楚：谁能产生什么、谁能消费什么、哪些关系被禁止。
- 每个抽象写：它是什么、从步骤 1/2 哪几条推出来、不变量、考虑过的替代和为什么不选。
- 不变量优先于结构：先说"任何时刻成立什么"，再说"由谁保证"。
- 术语：一个词在哪个上下文里什么意思；跨上下文的翻译显式化。

**写清**：概念模型（几个抽象 + 关系图）；每个抽象的推导；不变量清单；允许 / 禁止关系表；术语表。

**验证**：把步骤 1 每条需求、步骤 2 每个场景用模型**走一遍**（走查在步骤 5 正式做，这里先粗走）；走不通说明模型缺概念或选错抽象——回来改模型，不加补丁。

**走偏**：
- 从某个范式（effect system、actor、event sourcing、微服务）出发套模型，而不是从问题推出；范式是编码不是公理。
- 只写"写路径"或只写"读路径"，另一半压缩成一个词。
- 抽象没有推导，只有声明；替代方案为零。
- 抽象和实现语言绑死（"TypeScript 必须承担的保证"应是"类型必须承担的保证"）。
- 用工作流/连线的比喻建模纯函数与效应的关系。

## 步骤 4 结构

方法：ADD 递归分解 + Parnas 模块指南与接口规格 + C4 层级 + Kruchten 多视图。

**注重**：
- 把当前元素分解到**下一层**：系统上下文文档分到 container，container 文档分到 component。从步骤 3 的抽象出发分配到下一层元素；每个元素写它**拥有**什么、**隐藏**什么决定、**假设**什么。下一层元素有自己的文档时，它的内部写在那里，不在本文档展开；没有自己文档的直接由代码实现。component 文档不再分解出下级文档，它的结构就是步骤 3 的内部抽象及其关系，代码归 L4。
- 接口是契约不是签名：语义、交换的信息、质量要求、错误处理、undesired events（Parnas & Clements）。同层元素之间的契约写在它们共同上级的文档里，因为只有这一层同时看得见两端。
- 进程与信任边界：进程边界、信任边界，以及步骤 3 的有界上下文落在哪些元素之间；跨边界只传什么。
- 视图：逻辑（下层元素与责任）、进程/并发、部署、数据/持久化归属；每个视图回答一类关切，共用同一套概念和决定，不各自建立规则。
- 依赖方向（uses hierarchy）：谁依赖谁，能否分阶段交付、能否降级运行。
- 归属：每份持久化状态谁写谁读、怎么传播。

**写清**：下一层元素指南（每个元素的责任、隐藏的决定，以及分配给它的需求、契约与质量场景；有自己文档的元素逐项链接到下级文档承接的章节，这就是本文档的输出衔接；没有自己文档的元素由代码实现，不向下链接，代码位置列入实现参考）；同层元素间的接口规格；uses 图；部署/进程视图；持久化归属表；配置与凭据归属。图统一用 Mermaid，只画本文档分解出的元素（component 文档画它的内部抽象）及直接相邻的外部元素；视图是正文的章节，不是独立文档。

**验证**：每个元素能指回步骤 3 的抽象；没有元素承担多个抽象的秘密；接口规格足以让两个人各自实现两端后接得上；本文档没有展开任何有自己文档的下一层元素的内部。

**走偏**：
- 先画进程/仓库/目录再找模型（结构先于模型）。
- 组件有名字没有责任和隐藏的决定。
- 接口只有类型签名。
- 把"现在的部署形状"当不变量（launcher、打包、注入方式）。
- 把打包/分发成本当架构约束否决方案，而它并不在步骤 2 的约束表里。

## 步骤 5 走查

方法：Kruchten 场景驱动迭代 + Cockburn 用例扩展 + 故障路径。

**注重**：用步骤 4 的结构把每个关键场景、每条已知故障路径、每个状态转换**逐跳**走，每一跳的粒度是本文档分解出的元素：系统上下文文档走 container 之间，container 文档走 component 之间，component 文档走它的内部抽象之间；每一跳写输入、经过哪个元素/抽象、输出。走不动的地方是卡点，按"缺概念 / 选错抽象 / 接口不够 / 归属不明"判断回哪一步，修正后重走。

**写清**：逐场景 trace（正常路径 + 扩展/失败路径）；崩溃矩阵（每个崩溃窗口重启后的状态与恢复动作）。走查是设计的一部分（Kruchten 的 scenario view），写进文档而不是外部验证记录；写进去的是修正后走得通的结果，卡点与修正过程不进文档。

**验证**：卡点归零：卡在"缺概念"或"选错抽象"回步骤 3，卡在"接口不够"或"归属不明"回步骤 4。

**走偏**：
- 只走正常路径。
- 卡点当作"要补一节"，而不是模型或结构有错的证据。
- 走查用的是新旧混合的概念，或走的是理想化场景而不是步骤 1 列出的真实需求。

## 步骤 6 评估

方法：ATAM + 替代方案分析。

**注重**：
- 替代方案：每个重要决定至少一个可信的替代，写它在步骤 2 各场景下的后果，说明为什么不选。Google 称 `Alternatives considered` 是最重要的节之一；"an implementation manual with no trade-offs or alternatives is a sign that a design doc may not be worthwhile"。
- 风险 / 非风险：每条对应一个决定；写它影响哪个质量响应和理由。
- 敏感点：改这里某个质量响应会剧变。权衡点：改这里影响多个质量属性。
- 证伪条件：什么观测会推翻本设计。
- 最便宜的可信实验：原型、微基准、model checking，在改动还便宜时当下就做，验证可行性。

**写清**：替代方案对比表；risks / sensitivity / tradeoff 清单；证伪条件。

**验证**：每个重要决定有可信替代和理由；除用户明确交代留到下一阶段的项目外没有未定项目，也没有把未定伪装成已定。

**走偏**：
- 替代方案是稻草人。
- 用循环论证当理由（先选了 A，再拿"B 没有 A 的特性"否 B）。
- 拿现有实现的调查结论当新方案的评估。

## 步骤 7 维护

方法：先判断架构变化是否要求重组文档，再按当前设计的适用范围决定内容的保留、改写、合并或删除。

**注重**：实现或实验推翻假设后，直接改写当前决定及其推导，同时修正受影响的模型、结构、接口、视图和走查；发布后仍如此。决定的背景、理由和后果留在它所解释的设计旁边，不从正文抽走。

**重组**：大型架构调整改变了核心抽象、责任边界、元素划分或关键关系时，先按新的 C4 分解重建文档树与各文档主线，再组织全文：新增、合并或删除元素文档，把仍有效的需求、理由、证据和走查放到它现在所属的层级与元素中重新衔接，删除失去意义的旧章节与文件；不能以原目录为框架逐段替换术语、追加小节或补丁式修改。文档应直接解释新架构，而不是要求读者从旧结构中推算新结构。

**删除**：决定撤销、功能退出范围、假设失效或内容已被整合时，核实哪些篇章已不再约束当前设计，直接删除这些篇章及随之失效的图表、示例和说明；不要只加"已废弃"标记后继续保留。文件（正文或附件）已无独立的有效内容时，删除文件，不留空壳、跳转页或重复副本。同步清理目录项、链接、章节引用和其他文档中的依赖表述。仍支撑当前决定的理由、替代方案比较与证据必须保留；仍被工具或代码消费的契约不能只因说明被合并而删除。

**写清**：当前决定为什么成立、影响哪些元素和场景、什么条件下需要重审。

**验证**：文档树对应当前 C4 分解，每份文档的分组、层级和叙述顺序直接解释当前的核心抽象、责任边界及关键关系，而非暗示旧架构；受影响的每份文档仍满足「文档形态」的全部规则。逐一检查受影响内容和引用：保留的仍适用，撤销的规则没有在别处继续生效，删除后没有悬空引用，也没有丢失理解当前决定所需的理由与证据。

**走偏**：架构已经重构，文档仍沿用旧目录，只在原章节里打补丁；正文只剩结论，理由散在其他文件或对话里；用追加更正代替改写旧正文；只更新不删除，失效篇章越积越多；删了正文却留下旧文件和引用；文档实现后再不维护。

## 文档形态：按 C4 层级组织

**文档树对应系统的 C4 分解。** 一份文档描述一个元素在一个层级上的设计，由一份正文和若干附件组成：正文完成步骤 0–7 的论证，附件承载论证引用的次要内容。本 skill 中「文档」指正文连同附件，专指正文时写「正文」。L4 不单独成文；哪些层和元素不单独成文见「只建有价值的层」。按功能平铺的文档把同一元素的设计散到多份文档里，又把不同层级的内容混在同一份里：读者找不到某个元素的完整设计，也分不清哪段在讲系统、哪段在讲某个模块的内部。

|层级|正文描述的元素|写什么|不写什么|
|---|---|---|---|
|L1 系统上下文|整个系统及其所处环境|用户与外部系统、共享现象、需求与质量场景、非目标；系统拆成哪些 container、为什么这样拆；container 之间的契约与跨 container 的场景走查|任何 container 的内部结构|
|L2 container|一个独立运行或部署的单元：服务、进程、数据库、CLI、前端应用|上级分配给它的需求与契约、它拥有的状态、进程/部署/持久化视图；内部拆成哪些 component 及其契约与走查|其他 container 的内部；component 的内部实现|
|L3 component|container 内位于同一接口后的一组代码|它隐藏的决定、接口规格、不变量、内部走查|代码级细节|
|L4 code|类型、函数、schema|不单独成文：被工具或代码消费的定义就在代码里，上层正文解释其语义。需要长篇说明的代码级内容（字段逐项说明、算法细节、数据迁移映射）写成 L4 附件，挂在最近的有文档的上级元素的文档下|—|

### 归属

- **一份文档只站一层。** 一段内容归哪份文档，看它涉及的元素集合：写在这些元素最小的共同上级的文档里。只涉及某个下级元素内部的，移到该元素的文档；涉及同级元素之间关系的（包括它们之间的契约），移到上级文档。
- **功能不成文档。** 一项功能是穿过若干元素的场景：它的端到端走查写在这些元素最小的共同上级的文档里（跨 container 的写在系统上下文文档，只跨同一 container 内 component 的写在该 container 文档），各元素为它承担的责任写进各自的文档。
- **只建有价值的层。** 只有一个 container 的系统不写 container 层：系统与这个 container 视为同一元素，系统上下文文档同时承担 L1 与 L2 两行的内容，写它的部署/进程视图并直接分解到 component；步骤 4、5 对它而言的下一层元素是 component。component 隐藏一个其他 component 依赖的决定、有自己的接口规格与不变量时单独成文；否则它只作为上级文档里的下一层元素出现（责任与契约），内部直接由代码实现。没有自己文档的元素，内部没有需要单独论证的设计决定，由代码和实现参考承载；出现这样的决定，说明它应单独成文。本 skill 其他规则说「该元素的文档」时，对没有自己文档的元素指最近的有文档的上级元素的文档。新的文档只因层级或元素不同而拆出，不因读者不同而拆。
- **同一元素的论证不拆。** 逻辑、进程/并发、部署、数据归属，以及问题域、模型、约束、契约，都是同一元素设计的组成部分，论证全部写在该元素的正文里，不另建问题域文档、模型文档、约束文档或契约说明再靠总览串起来。

### 设计边界与衔接

边界防止设计扩散，衔接让设计之间有可核对的逻辑连接。

- **设计边界**：每份文档写明它决定什么；上级已定的只作输入，下级和同级元素的内部交给它们的文档，非目标不做。边界外的内容不在本文档展开，移到它所属的文档或删除；讨论中冒出的新问题先判定归哪份文档，再在那里决定。
- **衔接**：输入逐项链接到出处——下级文档链接到上级给出它的章节，系统上下文文档链接到需求来源与域证据；分配给下级的输出逐项链接到下级文档承接它的章节；没有自己文档的下一层元素由代码实现，代码位置列入实现参考。同级元素只经共同上级定义的契约衔接，不互相引用对方内部。契约只在给出它的一侧维护：承接的一侧链接过去，可以简述理解本文档决定所需的要点，但不改写、不另立版本。要改变承接的契约，就改上级文档，再同步受影响的下级文档。
- **闭合**：每项输入有用到它的决定，每项输出有承接，每个决定能追到某项输入或本文档内的推导。找不到的一端说明衔接断了，回到相应文档补齐，或删除多余的输入与决定。

### 正文与附件

- **正文不超过 300 行。** 限制只针对单份正文文件，不针对整棵文档树，也不针对附件，附件可以很长。正文超过 300 行说明划分有严重问题，原因只有两种：次要内容写进了正文，应移到附件；或元素边界有问题——它承担了不止一个抽象的秘密，或本该交给下一层的内部在本层展开——应回步骤 3、4 重新划分元素并拆出下级文档。不靠压缩措辞、删减论证或把论证挪进附件凑行数。
- **正文写论证，附件放次要内容。** 正文写决定、理由、设计边界与衔接、模型、契约语义和关键走查，并给出论证所需的要点：只读正文就能理解和评审全部决定。次要内容是论证引用、但不必逐条读完的材料：完整清单与大表（现有行为逐入口清单、域性质证据全集、全部质量场景、崩溃矩阵）、非关键场景的完整走查、实现参考（含 L4 附件）。附件不承载论证，不新增或改写决定。
- **附件从属于一份文档。** 附件放在所属文档的正文旁，以内容命名。承载设计参考的附件由正文在用到处链接；实现参考只从正文链接到「实现参考」附件这一处，L4 附件由「实现参考」附件链接，归属见上表。其他文档只链接正文。
- **文件树镜像元素树。** 目录层次与有文档的元素组成的树一致，正文以元素命名，具体路径遵从 repo 既有惯例。上级正文的分解章节直接链接下级正文，这些链接是分解说明的一部分，不另建索引页。

### 引用与定义

- **设计参考与实现参考分开。** 引用按用途分类，不按指向的对象分类：同一段源码，用来证明域性质或现有行为时是设计参考，用来告诉实现者改哪里时是实现参考。
  - 设计参考支撑论证：上级文档的契约与场景、需求来源原文、域性质与现有行为的证据（含源码行号）、外部规格。它们紧挨所支撑的结论；证据全集篇幅大时放进附件，结论旁链接到对应条目。设计结论和必要推导写在正文里，不留给引用去说。
  - 实现参考帮实现者落地，不参与论证：接口定义与 schema 所在文件、各元素与接口对应的代码位置、配置与凭据的注入位置、要改动的现有入口、调用层面依赖的库与 API，集中在所属文档的一份「实现参考」附件，按正文章节分组；L4 附件（字段逐项说明、算法细节、数据迁移映射）整体属于实现参考。论证需要其中某项事实作证据时，按用途把证据（源码行号、schema 位置）作为设计参考写在结论旁，正文不链接 L4 附件。需要约束实现的决定写进正文。
  - 设计、规划与评审只读正文和设计参考；实现参考到实现阶段才读，避免代码细节在决定成形前干扰判断。
- **被消费的定义留在消费位置。** IDL、OpenAPI、类型等实际被工具或代码消费的定义保留在代码或规格文件里；正文解释它们的契约语义、错误与设计理由，定义位置列入实现参考。不复制定义，也不让另一个说明文件重新决定语义。
- **决定和理由就近写。** 表、图、清单支撑论证，不代替论证；"每个事实只出现一次"是不维护重复定义，不是抽走理解当前决定所需的上下文。

### 变更与整合

- **变更写进受影响的层。** 新功能或架构调整修改它影响到的各层文档：改契约的改上级，改内部的改元素自己的文档。不另写一份按功能命名的变更设计文档与现有文档并存。尚不存在的新系统从它的系统上下文文档写起。
- **在分支上完成，合入即当前设计。** 设计变更在同一分支或 PR 中完成走查、写全替代方案与风险，经审批者确认后合入。
- **整合已有文档。** 已有平铺或混层的文档：先定出当前的 C4 元素树，再把每段仍有效的结论、理由和证据按上面的规则移到对应元素的正文或附件，删除功能文档、重复篇章和失效内容；原文件已无独立有效内容时一并删除，并清理目录与引用。不新建索引链接到原有碎片。实际消费的定义与仍被引用的证据不因整合而删除。
- **文档不自称"权威""唯一入口"。** 层级归属由内容涉及的元素决定；发现冲突就核实并修改冲突内容。

## 审查清单

审设计文档时逐条问：
1. 能一句话说出这份文档描述哪一层的哪个元素、要决定什么、给谁看吗？设计边界写清了吗：不决定的事归哪份文档，有没有越界替上级、下级或同级做决定？
2. 衔接闭合了吗：每项输入链接到出处并被本文档的决定用到，每项输出有承接？下级承接的契约与上级是否一致，有没有自行改写的版本？
3. 问题域有没有独立于解决方案写出来？域性质有证据吗？
4. 质量要求是场景还是形容词？有 response measure 吗？
5. 核心抽象有几个？每个从哪推出来？替代是什么？
6. 每个元素说清拥有什么、隐藏什么决定了吗？接口有语义和错误吗？
7. 关键场景和故障路径走通了吗？走查在文档里吗？
8. 替代方案、风险、权衡、证伪条件在吗？
9. 除用户明确交代留到下一阶段的项目外，还有未定项目或"待确认"吗？正文有没有实验痕迹？文档里有没有实验的计划、过程或状态标记？
10. 实现者能不看对话独立实现一块并和别人接上吗？
11. 一年后维护者能找到"改这里影响什么、为什么有这条边界"吗？
12. 文档树是否对应当前 C4 分解？每份文档是否只站一层？有没有按功能命名的文档？大型调整后，是否仍把新设计塞在旧架构的文档和章节中？
13. 每份正文在 300 行以内吗？超过时是次要内容进了正文，还是元素边界有问题？只读正文能否理解并评审全部决定？附件有没有承载论证或新增决定？
14. 设计参考与实现参考分开了吗？实现参考（含 L4 附件）有没有夹带正文没有的决定？
15. 同一元素的前提、决定、理由和关键验证在它的正文里连得起来吗？是否仍有外部碎片另立规则，必须来回拼接才能理解？
16. 已不再适用的篇章、无独立有效内容的文件及其引用是否已删除？删除后是否仍能完整理解当前决定？

任何一条答不上，文档就还是笔记。

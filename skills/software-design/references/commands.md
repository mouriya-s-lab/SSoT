# 并行编写的指令表

几个 agent 同时编写同一份设计的 VDM-SL 规格时，彼此只用本表的指令通信。指令的名字、参数和回复格式都是固定的：一条消息说什么、收到后该做什么，都不靠理解对方的措辞。

## 分工

- **主控**：一个 agent。只有它运行 `init`、`module`、`unit`，编辑 `design.tex`，分配归属，并做最终的集成检查。
- **写手**：其余 agent。每个写手拥有若干模块目录，只写自己目录里的文件：该目录的 `README.tex` 与 `.tex` 规格文件，不包括子目录。
- **归属单位是模块目录**。一个目录只有一个写手；一个写手可以拥有几个目录。目录到写手的对应写在 `分配` 指令的归属表里，所有写手收到的是同一张表。

写手需要别人的东西，就向拥有者发指令，不改别人的文件。还没有拿到的名字照样引用，`check` 会把它报成断口；断口不妨碍继续写自己的部分。

写手在自己目录里新建的 `.tex` 文件，由主控加进 `design.tex` 的阅读次序：写手在 `完成` 的 `文件` 字段里列出它们。在此之前 `check` 报的“不在阅读次序里”落在 `design.tex` 上，写手不处理。

## 消息格式

```text
<指令> <主参数>
<字段>: <值>
<字段>: <值>
```

- 第一行是指令名和主参数，之后每行一个字段，字段名只用本表列出的。
- **名字一律写成限定名**：`模块`名字`，字段写成 `模块`名字.字段`。不用别称、缩写或自然语言描述代替名字。
- **种类只用 VDM-SL 的关键字**：`types`、`values`、`functions`、`operations`、`state`。
- **签名写成 VDM-SL**，与 `exports` 里的写法一致，例如 `Start: RequestNo ==> StartOutcome`。
- **文件写成相对 `design/` 的路径**，例如 `architecture/run.tex`。
- **诊断原样转发** `check` 输出的整行，例如 `architecture/run.tex:60: [structure] …`，不改写、不概括。
- 一条消息只发一条指令。
- 每条 `需要` 恰好得到一条回复：`已导出` 或 `不归我`。同一个名字换了签名再发 `需要`，也要再回复一次。

## 指令

| 指令 | 发送方 → 接收方 | 主参数 | 字段 | 接收方必须做的事 |
|---|---|---|---|---|
| `分配` | 主控 → 写手 | 写手名 | `目录`（一个或多个）、`内容`（这些目录拥有哪些连接与数据、不拥有哪些，或旧文档中的位置）、`归属表`（全部目录 → 写手与该目录的 VDM-SL 模块名）、`已有导出`（可以直接 import 的限定名与签名） | 只在所分配的目录里写，模块名按归属表起；写完发 `公告`，全部做完发 `完成` |
| `需要` | 写手 → 拥有者 | 限定名 | `种类`、`签名`、`用途`（一句，用规格里的名字）、`请求方`（请求方的模块名） | 在自己的模块里定义并导出它，回复 `已导出`；判断它不属于自己的模块，回复 `不归我` |
| `已导出` | 拥有者 → 请求方 | 限定名 | `种类`、`签名`、`位置`（文件:行）、`说明`（可选：签名与请求不同的原因） | 按回复的签名 import 并使用；签名与 `需要` 里的不同，以 `已导出` 为准 |
| `不归我` | 拥有者 → 请求方，抄送主控 | 限定名 | `理由`（用规格里的名字）、`建议拥有者`（模块目录）、`正确限定名`（可选：东西归我，但名字写错了） | 有 `正确限定名` 时按它重发 `需要`；否则改向建议的拥有者发 `需要`；没有建议时发 `冲突` 给主控 |
| `公告` | 拥有者 → 全部写手 | 模块名 | `导出`（这个模块已经导出的全部限定名与签名） | 需要这些名字时直接 import，不再发 `需要` |
| `签名变更` | 拥有者 → 全部写手 | 限定名 | `旧签名`、`新签名`、`原因` | 引用了它的写手按新签名修改自己的文件 |
| `改名` | 主控 → 全部写手 | 旧限定名 | `新限定名` | 把自己文件里的旧名全部换成新名，包括 `\vdmref`；回复 `完成` |
| `新模块` | 写手 → 主控 | 模块目录 | `理由`、`父目录`、`建议写手` | 主控用 `module` 或 `unit` 建目录，并重新发 `分配`（含更新后的归属表）给相关写手 |
| `冲突` | 写手 → 主控 | 诊断原文，或 `不归我` 的原文 | `涉及`（限定名或文件）、`已试`（已做过什么） | 主控判断由谁修改，向该写手发 `重做`，或调整归属 |
| `重做` | 主控 → 写手 | 文件 | `诊断`（原文）、`要求` | 只改这个文件，消除这条诊断；改完运行 `check`，发 `完成` |
| `完成` | 写手 → 主控 | 写手名 | `文件`（含新建的文件）、`导出`（限定名与签名清单）、`断口`（自己文件里剩下的断口，诊断原文）、`未定义务`（自己文件里的未定证明义务） | 主控把新文件加进阅读次序；全部写手完成后运行 `check` 做集成 |
| `停止` | 主控 → 写手 | 写手名 | `原因` | 停下手里的修改，保持文件可解析，发 `完成` |

## 检查

- 写手发 `完成` 之前必须运行 `check`，`完成` 里的 `断口` 与 `未定义务` 取自这次输出；只处理落在自己文件里的诊断，别人的文件里的诊断不处理，也不转述。
- 自己文件里的诊断分两类：断口（引用的名字还不存在）等对方 `已导出` 或 `公告`；其余的诊断是冲突，先在自己的文件里改，改不了再发 `冲突`。
- 主控在所有写手发出 `完成` 之后运行 `check` 与模型审查。剩下的断口说明有 `需要` 没有回复，剩下的冲突用 `重做` 分派。
- 两个模块各自定义了意思相同的连接（例如根模块与子模块都有“提交”）时，`check` 不会报错；主控在集成时对照归属表与 `graph` 查出来，用 `重做` 让不拥有它的一方删掉，改为 import。

## 示例

用 [示例设计](example/design/) 说明。主控把根目录分给写手 A，`architecture/attempt` 分给写手 B，`business/report` 分给写手 C：

```text
分配 C
目录: business/report
内容: 每天生成一份日报：开始当天的运行，记下被接受的尝试，再结束它
归属表: architecture -> A（Run）; architecture/attempt -> B（Attempt）; business/report -> C（Report）
已有导出: Run`Start: RequestNo ==> StartOutcome; Run`Finish: RunId ==> ()
```

C 写场景时需要记下尝试，向拥有 `architecture/attempt` 的 B 发：

```text
需要 Attempt`Record
种类: operations
签名: Record: Entry ==> ()
用途: Report`Daily 在运行开始后记下被接受的尝试
请求方: Report
```

B 定义并导出之后回复：

```text
已导出 Attempt`Record
种类: operations
签名: Record: Entry ==> ()
位置: architecture/attempt/attempt.tex:33
```

A 写完 `Run` 之后公告它的全部导出，C 从中直接 import `Run`Started`，不必再发 `需要`：

```text
公告 Run
导出: Run`RunId: RunId; Run`RequestNo: struct RequestNo; Run`Started: struct Started; Run`StartOutcome: struct StartOutcome; Run`StatusOutcome: struct StatusOutcome; Run`RetrySeconds: nat1; Run`Start: RequestNo ==> StartOutcome; Run`Status: RequestNo ==> StatusOutcome; Run`Finish: RunId ==> (); Run`Recover: RequestNo ==> ()
```

全部完成后，主控把新文件加进阅读次序并运行 `check`，示例设计的输出是“通过：3 个模块”。

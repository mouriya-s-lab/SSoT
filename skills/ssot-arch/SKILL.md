# ssot-arch：核心抽象与架构设计

## 这个阶段解决什么问题

在写任何业务单元或抠 VDM-SL 语法细节之前，定下系统的**核心抽象边界**与 **`design/architecture/` 的模块树、对外连接、核心状态与不变量、以及支撑它们的依据与理由**。

示例设计的架构部分见 [`../ssot/references/example/design/architecture/`](../ssot/references/example/design/architecture/)。

---

## 一、设计是什么：划定抽象边界

设计是代码化的文档。它的价值是作为参考，陈述程序的核心与不变量；实现对照它检验，它不随实现改变。

1. **设计只写核心，常变的业务留在代码里。**
   核心定下之后不再常改；建在核心之上、随需求变动的业务写在代码里，不写进设计。示例设计只写 `Run` 与 `Attempt` 两个核心模块；`Report` 只写日报怎样在它们上面运行，日报的内容不在设计里（[`business/report/README.md`](../ssot/references/example/design/business/report/README.md) 明写“不负责日报的内容”）。
2. **核心判据：在连接不变时可以替换的做法属于实现。**
   一段内容只规定怎样兑现连接，换一种做法时连接与不变量都不变，它就是实现，不写进设计。**两个独立的实现者各写一份时必须得出同一外部行为的核心内容，才写进设计。**
   例如 `Run`Start` 只有 `post`：它规定开始之后运行表必须是什么样，不规定怎样查找、怎样插入。[`appendix/reference/run-store.md`](../ssot/references/example/design/appendix/reference/run-store.md) 写了一种实现，换成别的实现，`Start` 的签名与后置条件都不变，所以那份材料在附录，不在规格里。
3. **抽象边界内外分明：边界之外不存在。**
   系统通过声明的连接与类型划定抽象边界：只承认经声明边界交出的值与结局；被抽象掉的内部细节（如外部进程未声明的副作用、底层传输协议、内存锁、文件格式、存储介质）在抽象中不存在。
4. **失败与并发按同一判据划分。**
   会改变部件、连接、状态空间或使用方可观察承诺的决定属于设计，例如是否承诺恰好一次、“结果未知”是不是一种结局、崩溃后由谁接管。罕见不等于是实现。
   例如结果未知改变了使用方必须处理的结局，所以它是 `StartOutcome` 的一支 `<Unknown>`，并且说明里写明恢复走 `Status`。
5. **设计不展开边界情况与逐情形处理。**
   不改变连接、状态空间、不变量和可观察承诺的处理细节属于实现，例如逐项的拒绝原因、编码与字节、在既定承诺下选哪种算法。一段细节保护某条不变量时，设计只写这条不变量。
   例如被拒绝只有一支 `<Rejected>`；逐项列出拒绝原因就是展开了边界情况：
   ```vdm
   -- 反例：逐项列出拒绝原因
   StartOutcome = Started | <QuotaExceeded> | <BadRequest> | <UpstreamBusy> | <Unknown>;
   ```
6. **设计不要求组合成整体。**
   组合根、适配器、总入口、完整调用链、为通过检查补的实现都不属于设计。设计只要求本身合法、引用能解析。
7. **设计与实现的类型是两码事。**
   设计不依赖实现，因为设计不能随实现改变；规格是 VDM-SL，实现无法 import 它，实现用自己的语言表达同样的类型并对照规格检验。
8. **从问题域与外部事实出发，不参考实现代码。**
   从零写设计或用 SSoT 重写旧文档时，只依据问题域约束与外部可观察承诺建模，不阅读或参考实现代码与实现架构文档，不把代码里的内部 `struct`/`enum`、数据库表或内部组件分工反向翻译进 `design/`。

## 二、架构与优先级

架构回答三个问题：

1. **由什么组成**：有哪些模块，各是什么，谁在谁里面。
2. **用什么组成**：模块由哪些核心元素拼成，彼此经由哪些连接相接。
3. **为什么**：为什么是这些模块和这些材料，依据哪些事实、约束与需求。

业务建在架构上，只经连接接入。架构贴近抽象，业务贴近实现；两者分开写，混在一起时谁都看不出架构是什么样。

### 依赖方向与边界

- **单向依赖：** 业务引用架构，架构绝不引用业务。
- **架构纯度：** 架构里不得有只为某一个业务单元存在的类型、角色、分支或策略规则。
- **架构由需求证明：** 改变架构的需求与质量要求写进架构的「依据」，写明来源；依据可以说明它来自哪类业务场景，但架构不引用业务单元的规格。
- **附录不设立规则：** 正文可以指向附录中的证据，附录可以引用正文，但附录本身不设立任何规则。

## 三、两条轴：抽象层级与模块三部分

抽象层级与模块划分是两条独立的轴：

- **抽象层级**是模块树的深度：根模块（`architecture/`）之下是子模块（`architecture/<child>/`）。父模块粒度粗，子模块粒度细。
  - 子模块可以使用祖先拥有的材料（如子模块 `Attempt` `imports from Run types RunId renamed RunId`）；
  - **父模块绝不依赖子模块**；几个子模块共用的材料放在它们共同的父模块。
- **模块划分**是每个架构模块固定的三部分，不论它在哪一层：
  - **外部连接**：别的模块能用的操作、函数与类型（`exports`）；
  - **核心代码**：本模块拥有的类型、不变量、状态、函数与操作（`definitions`）；
  - **内部设计**：子模块（子目录），以及规格说不清的本模块语义（`README.md` 的「语义」或主题文件）。

**模块的划分只按抽象：** 一组可以对外陈述连接、内部决定可以对其他模块隐藏的元素，成为一个模块。篇幅或执行步骤不是拆分模块的理由。例如 `Attempt` 单独成为子模块的理由写在它的 `README.md`：

```markdown
尝试的记录只追加，所以单独成为子模块：它只用到父模块的 ``Run`RunId``，父模块不需要知道记录怎样保存。
```

## 四、视角与持有者

同一样东西，在持有它的模块里是细节，在别的模块里是概括性的占位符，实际需要时才展开。以信号灯为例：

```vdm
SignalColour = <Red> | <Amber> | <FlashingAmber> | <Green>
```

1. **定义在持有者。**
   信号灯有这几种状态，所以 `SignalColour` 定义在信号灯的模块里；`=` 右边是信号灯自己的细节。在示例设计中，运行身份 `RunId` 与开始的结局 `StartOutcome` 定义在持有运行表的 `Run` 里；`Attempt` 用到运行身份，但不定义它。
2. **观察者需要才展开。**
   观察者需要知道状态并按它分支时，持有者才带 `struct` 导出细节（如 `Report` 要按开始的结局分支，所以 `Started` 与 `StartOutcome` 带 `struct` 导出）；观察者不需要知道内部构成时，持有者定义为 `token` 且不带 `struct` 导出（如 `RunId` 在 `Report` 里只是占位符，只能原样传给 `Finish` 与 `Record`，不能读结构、不能自造）。
3. **行为归做出行为的一方。**
   信号灯是红灯时不允许通过路口，这是司机的行为，不是信号灯的行为，写在司机那里。运行开始之后记下尝试、再结束运行，是日报的行为，写在 `Report`Daily`；`Run` 只交出结局。
4. **规则归持有者。**
   信号灯能从红色切换到绿色，是因为满足一条倒计时状态规则。离线信号灯自己持有这条规则，它在信号灯里是细节；联网信号灯是这条规则的消费者，它在信号灯里只是概括。在示例设计中，哪些运行需要找回由 `Attempt` 持有，在 `Attempt`Unresolved` 里写出细节。
5. **隐含前提是软件的一部分，就有它的位置。**
   车不能飞在天上，必须行驶在路上。这样的前提如果是软件的一部分，它在程序里可以解释：它是外部依赖时，在这里是导入的占位符；它在本系统里实现时，可以在实现它的模块找到细节（如 `Attempt` 的记录属于某次运行，`imports from Run types RunId` 就是占位符，指向 `Run` 的定义）。隐含前提不是软件的一部分时（例如服务器需要电力运行），不写进设计。
6. **展开是可选的，但全局只有一次。**
   一样东西可以不展开（`token`），但展开只能有一处；展开了两处，它就有多重解释。展开它的模块是持有者，只用占位符的模块是观察者或消费者。

### 由观察者反推持有者是否展开（防架构过度展开）

“定义在持有者，观察者需要才展开”不仅决定 `exports` 是否带 `struct`，更决定**持有者模块自己内部要不要展开结构**。在 `architecture/` 中定义任何类型或状态分量前，先用下表反推：

| 候选类型 / 状态分量 | 外部观察者（`business/`）如何使用它 | 持有者模块内部的写法 |
|---|---|---|
| 外部观察者必须在它的分支上做不同决定，或读取它的字段（如 `StartOutcome = Started \| <Rejected> \| <Unknown>`） | `Report` 在 `cases Start(request)` 中按分支走不同路径 | **展开**（定义 `::` 或 `\|`），并带 `struct` 导出 |
| 外部观察者只原样传递凭据，靠调用持有者的连接操作获取判定结局（如 `RunId`、观察位置 `LogPosition`、写尝试身份 `AttemptId`） | 外部只调 `Finish(run)` 或 `CheckBasis(basis)` 看 `<Fresh> \| <Stale>`，从不读内部流名、序号或中间阶段 | **保持 `= token`**（即使在持有它的架构模块内部也只写 `token`，不展开内部存储字段、阶段状态机或引用计数凭据） |

## 五、连接、状态与生命周期

连接是一等概念：模块之间只经连接相接，连接写清楚之后，两边可以各自替换实现。

| 概念 | 是什么 | 示例设计中的对应 |
|---|---|---|
| 连接点 | 一个可以被调用的操作或函数 | ``Run`Status``：一个导出的操作 |
| 连接面 | 共享同一份状态与同一条不变量的一组操作；共享的那条不变量就是这个面的规则 | `Start`、`Status`、`Finish` 共享状态 `Runs`；共同规则是 `inv mk_Runs(b, l) == l subset rng b` |
| 交换 | 连接收进与交出的数据 | 参数与结果类型，如 `Start: RequestNo ==> StartOutcome` |
| 结局 | 一次调用的全部可能结果；只列使用方必须区分处理的结局，不逐项列原因 | 并类型 `StartOutcome = Started \| <Rejected> \| <Unknown>` |
| 可观察的失败 | 结局中的一支，例如结果未知；写明恢复要走哪个连接 | `<Unknown>` 一支，说明里写明改用 `Status` 找回 |
| 准入定律 | 实现必须满足的不变量、前置条件与后置条件，三者各管一件事；签名对得上不等于可以接入 | `Start` 的后置条件：同一请求号重复开始，得到同一运行 |
| 不承诺 | 对使用方隐藏结构的类型：使用方只能原样传递，不能读、不能造 | `RunId = token`，导出时不带 `struct` |
| 生命周期 | 一样东西从开始到结束：由哪个连接开始、哪个连接结束，嵌套在谁之内，由谁确认 | 运行由 `Start` 加入 `live` 开始、由 `Finish` 移出结束；`l subset rng b` 规定活着的运行都嵌套在某个请求之内 |
| 判定 | 两个实现必须得出同一结果的计算；这时计算本身就是设计决定 | ``Attempt`Unresolved`` 写出显式体，因为两个实现必须得出同一集合 |

### 建模准则

- **说做到什么，不说怎么做。** 结果用性质刻画、可以有多个合格的结果、或者不想绑定一种算法时，写隐式定义（只写 `pre` 与 `post`）；结果唯一确定、两个实现必须算出同一值时，直接写显式纯函数。
- **不变量、前置条件、后置条件各管一件事。**
  - **不变量（`inv`）**附在一个类型或一份状态上：这个类型的每一个值、这份状态的每一个时刻都成立；状态的不变量相当于并进了每个操作的前置与后置条件，它不说状态怎样变化。
  - **前置条件（`pre`）**写一个函数或操作在什么情况下可以调用。
  - **后置条件（`post`）**写结果与输入、调用前后的状态之间的关系，对输出的要求写在这里。
  - 一条“必须”先判断属于哪一种，不因为句子里有“必须”就写成不变量。以 Overture 的交通灯示例为例：互相冲突的两条路径至少一条是红灯，任何时刻都成立，是路口 `Kernel` 的不变量；只有黄灯才能转红，是 `ToRed` 的前置条件：
    ```vdm
    Kernel :: lights    : map Path to Light
              conflicts : set of Conflict
    inv mk_Kernel(ls,cs) ==
          forall c in set cs &
                mk_Conflict(c.path2,c.path1) in set cs and
                c.path1 in set dom ls and c.path2 in set dom ls and
                (ls(c.path1) = <Red> or ls(c.path2) = <Red>)

    ToRed: Path * Kernel -> Kernel
    ToRed(p,mk_Kernel(lights,conflicts)) ==
      mk_Kernel(ChgLight(lights,p,<Red>),conflicts)
    pre p in set dom lights and lights(p) = <Amber>;
    ```
- **从函数与值出发，不变量越简单越好。** 不变量复杂，往往说明状态选得不对；不为了让操作好写而在状态里放冗余缓存或派生字段，冗余会带来多余的同步不变量。能由核心事实通过纯函数投影算出的东西，一律写成纯函数，不放进 `state`。
- **生命周期严格按嵌套次序闭合。** 先找出有生命周期的对象，写清各自的开始锚点、结束锚点及其确认者，判断是否嵌套：内层必须在外层开始锚点之后开始；结束外层前必须先结束其全部内层，最后才写外层的结束锚点。
- **只写可观察的不变量与连接，不写保护不变量的内部机制。** 例如“被单据引用的观察依据必须有效”只写成 `CheckBasis` 连接与 `<Fresh> | <Stale>` 结局，不在架构里发明引用计数机制（`RefHolder`、`AcquireRef`/`ReleaseRef`）；“写尝试在发送前固化且结果未知时阻塞通道”只写成 `Prepare`/`Send`/`Resolve`/`Abandon` 与阻塞集合不变量，不在架构里手写两阶段落盘屏障（`Barrier`、`CompleteSend`）。
- **正交的架构底座保持零耦合。** 各自独立表达一类外部边界或核心状态的架构模块（如来源能力、观察日志、受控写边界）彼此不 `import`；不要在一个架构模块内部替业务去调用另一个架构模块做前置检查或引用管理，跨架构连接的串联归 `business/`。

## 六、依据与理由

### 依据（`## 依据`）

依据是会改变设计的外部事实、约束、系统级需求与质量要求：

- **格式：** 每条一句话，写出来源，并接一句“所以……”，说明它让这个架构模块多了或少了什么。例如：
  ```markdown
  上游在超时之后仍可能已经开始了运行（来源：上游接口说明，证据见附录 `evidence/upstream-timeout.md`）。所以 ``Run`StartOutcome`` 有结果未知一支，调用方经 ``Run`Status`` 找回运行。

  在上游可用的情况下，调用方用同一个请求号重复调用 ``Run`Start`` 时，系统只产生一次运行（来源：示例需求）。所以 ``Run`Start`` 按 ``Run`RequestNo`` 幂等，运行表记下请求号到运行的对应。
  ```
- **质量要求：** 写成“在〈环境〉下，〈刺激〉发生时，〈响应〉满足〈度量〉”，并写出来源。数值只在有出处时写，不为凑格式编造指标。
- **放置层级：** 影响整个系统的依据写在根模块 `architecture/README.md`；只影响一个子模块的写在该子模块的 `README.md`；篇幅大的证据放进 `appendix/evidence/`，依据只引用它。
- **禁令：** 当前实现的目录、调用步骤、技术选型和偶然行为不是依据；不编号，不建追溯矩阵。

### 理由（`## 为什么`）

- 每个改变架构形状的决定都写理由，理由引用依据与规格元素。例如：
  ```markdown
  运行表与开始、找回、结束放在同一个模块，因为它们共享“活着的运行都来自某个请求”这条不变量（``Run`Runs``）。
  ```
- **写出可信替代的取舍：** 确实存在可信替代时，写一句为什么不选它。例如：
  ```markdown
  不让调用方自己记下请求号与运行的对应：结果未知时调用方手里没有运行身份，只有提供方能按请求号找回。
  ```
- 只关系到单个元素的选择，理由直接写进该元素的 `--` 说明注释。

## 七、阶段门控（进入 `ssot-business` 前必查）

完成架构设计后，逐项确认以下门控，全部通过才进入 `ssot-business`：

1. **三问清晰：** 只看模块划分与各 `README.md` 的负责范围，能否不借助实现术语说出系统由什么组成、用什么组成、谁在谁里面？
2. **抽象边界干净：** 是否把连接不变时可替换的做法、逐项失败原因、存储/编码/锁机制挡在了 `architecture/` 之外？
3. **单一持有者：** 每个核心概念、类型和状态不变量是否都放在真正的持有者模块，且全局只展开一次？共用的材料是否在共同父模块，父模块零依赖子模块？
4. **连接面自洽：** 共享同一份 `state` 的操作是否真的共享那条 `inv`？可观察失败是否都在结局中有分支并指明了恢复连接？生命周期开始与结束锚点的嵌套关系是否明确？
5. **依据有据：** 每条依据是否有真实外部来源与“所以……”？每个架构决定是否都有引用依据的理由？

# ssot-design：把形状写成设计

本块读目标仓库 `.tmp/ssot-draft/` 里的草稿，把其中的形状写进 `design/`。架构模块和业务单元按草稿定下的归属一起写，VDM 里的每个元素都守着草稿里的某条形状。没有草稿，或者要写的内容在草稿里找不到对应的形状时，停下，说明需要先用 `ssot-draft` 补草稿。

## 一、每条形状选一种写法

写法按形状说的是什么来选，不按哪种好写来选：

| 形状说的是 | 写法 |
|---|---|
| 什么东西能存在，谁能看到它的结构 | 类型。观察者只原样传递的写成 `token`，导出时不带 `struct` |
| 一个连接面上任何时刻都成立的关系 | 状态的 `inv` |
| 谁在什么条件下可以调用一个连接，调用前后什么变了、什么不变 | 隐式操作的 `pre` 与 `post` |
| 哪个模块能触达哪个模块 | `imports` 与 `exports` 的方向 |
| 某条形状依赖的判定 | 纯函数。两个实现必须得出同一结果时写显式体；只约束结果的性质时，写签名与后置条件 |
| 内层先于外层结束这类生命周期次序 | 场景操作，其中每一个先后都对应一条形状 |

形状写在草稿定下的持有者那里，只展开一处；别的模块需要它时，经导入引用。

## 二、不写什么

不守任何形状的内容不进 VDM：业务一步步怎样运行，例如推进次序、就绪条件、策略与挑选；边际处理，例如并发、超时、重试、崩溃与失败原因的细分；修改、介入这类编辑处理；记录与存储的样子；索引怎样存放与定位。草稿里有意不画的东西，这里也不写。

规格写不清、但确实属于形状的语义，例如定时、进程边界、包含关系、事实与副本，写进 `README.md` 的「语义」。

不为了让每条形状都有个落点去造东西。一条形状写不进规格时，不能造一个只有导入列表的单元、一条只走一遍调用的场景，或者一个没人读的状态字段来冒充。导入方向只约束规格里的模块彼此怎样依赖，管不到规格之外的使用方；一条场景只说明这条路没有破坏形状，不能证明形状成立。

## 三、写不进去时

- **只是写法不对：** 换一种写法，例如改成类型、改写到另一个连接的条件里，或者调整导入方向；持有者与含义都不变。
- **持有者或含义必须改变：** 停下，回到 `ssot-draft` 修改草稿并写明原因，不在落地时悄悄改掉归属。业务没有持久状态、架构不能引用业务、某个前置条件写起来更顺手，都不是改变持有者的理由。

`ssot check` 的诊断不是设计需求。一个定义没人用，要么它本来就不需要，应当删掉；要么草稿里本该使用它的连接还没写出来。不为了消除诊断而增加导出、拆分单元或添加场景。

## 四、目录与写法

- 用 `ssot init`、`ssot module`、`ssot unit` 建目录，每个架构模块、每个业务单元各占一个目录。`design/README.md` 的阅读次序要列出 `architecture/` 与 `business/` 下的每个 `.md`：`ssot module`、`ssot unit` 只加入它们生成的 `README.md`，规格文件要自己加进去。
- 模块与单元的 `README.md` 以一级标题开头，先用一段说明负责什么、不负责什么。之后，架构依次写「依据」「为什么」「语义」，业务依次写「依据」「需求」「为什么」「语义」，没有内容的小节不写。每条依据写出来源，并接一句“所以……”；业务的每条需求用双反引号指出兑现它的规格元素。
- 规格写在 ```` ```vdm ```` 代码块里，一个文件至多一个具名模块。每个定义与字段都要有 `--` 说明，写它是什么、承诺什么。状态的 `init` 写成 `s == s = mk_…(…)` 的形式。其余写法照示例设计 [`../ssot/references/example/design/`](../ssot/references/example/design/) 与本地 VDM 文档 [`../ssot-spec/references/vdm/`](../ssot-spec/references/vdm/README.md)。
- 文字里提到规格元素，一律用双反引号写限定名，例如 ``` ``Run`Start`` ```。不造规格里没有的词，也不复述规格已经说清的内容。

## 五、交付

写完后运行 `ssot check`，只用来排除解析、类型、布局与说明注释方面的错误；诊断按第三节处理。交付时向用户说明每条形状写在了哪里、用了哪种写法，以及哪些形状只写进了「语义」。

本块不给验证结论。设计交给 `ssot-verify` 在独立的上下文里验证；验证发现的问题，回到本块或 `ssot-draft` 修改。

# ssot-design：按草稿写设计

本块读目标仓库的 `.tmp/ssot-draft/README.md`，把其中的约束写进 `design/`，架构模块与业务单元按草稿的归属一起写。没有草稿，或者草稿没有满足它自己的完成条件时，停下，转 `ssot-draft`。

## 一、每条约束选写法

按草稿标出的类别选：

| 约束类别 | 写法 |
|---|---|
| 任何时刻都成立的关系 | 类型结构，让违反情形构造不出来；类型表达不了时写状态的 `inv` |
| 一次调用的准入条件 | 操作的 `pre` |
| 一次调用前后的关系 | 隐式操作的 `post`，`ext` 只列要写的分量；没列进 `ext wr` 的分量调用前后不变 |
| 生命周期的先后 | 显式场景操作，体内每一处先后都对应一条约束 |
| 哪个模块能触达哪个模块 | `imports` 与 `exports` 的方向；它只约束规格里的模块 |
| 一条判定 | 函数。判定结果本身就是草稿里的约束时写显式体，否则只写签名与 `post` |

选完自检：拿草稿里这条约束的违反情形，问“规格里哪个类型或哪条谓词排除了它”。指不出来就换写法。导入列表与单条场景排除不了任何情形。

约束写在草稿定下的持有者那里，只展开一处；别的模块需要时经导入引用。

## 二、元素的进入条件

每个类型、字段、函数、操作与场景，都要答得出：它表达草稿里的哪条约束，或者它是哪条约束所需的连接。答不出的不写。下面几种情况都属于答不出：

- 为了让一个名字在规格里有落点而造出的元素；
- 只因“两个实现必须算出同一结果”而写成显式体的函数；
- 场景体里有一处先后、分支或挑选，在草稿的约束里找不到。这是在模拟业务怎样运行，删掉。

`token` 与 `is not yet specified` 只用于不展开的内容。草稿里已经定下的约束必须出现在类型、`inv`、`pre` 或 `post` 上，不能藏进不展开的定义里。

规格写不清、但确实属于约束的语义，写进 `README.md` 的「语义」。

## 三、写不进去时

先判定是哪一种：

- **只是写法不对：** 换一种写法，持有者与含义不变；
- **对象、关系或归属不成立：** 停下，回到 `ssot-draft` 修改草稿并写明原因，不在落地时改掉归属。

归业务持有的约束写不进业务时，问业务做判定所需的事实，连接提供了没有。没提供就改连接要提供的内容，不把判定搬进架构。

`ssot check` 报某个定义没人用：要么它不需要，删掉；要么用它的那条连接还没写。不为消除诊断新增模块、导出或场景。

## 四、目录与写法

- 用 `ssot init`、`ssot module`、`ssot unit` 建目录，每个架构模块、每个业务单元各占一个目录。`design/README.md` 的阅读次序要列出 `architecture/` 与 `business/` 下的每个 `.md`：`ssot module`、`ssot unit` 只加入它们生成的 `README.md`，规格文件要自己加进去。
- 模块与单元的 `README.md` 以一级标题开头，先用一段说明负责什么、不负责什么。之后，架构依次写「依据」「为什么」「语义」，业务依次写「依据」「需求」「为什么」「语义」，没有内容的小节不写。每条依据写出来源，并接一句“所以……”；业务的每条需求用双反引号指出兑现它的规格元素。
- 规格写在 ```` ```vdm ```` 代码块里，一个文件至多一个具名模块。每个定义与字段都要有 `--` 说明，写它是什么、承诺什么。状态的 `init` 写成 `s == s = mk_…(…)` 的形式。其余写法照示例设计 [`../ssot/references/example/design/`](../ssot/references/example/design/) 与本地 VDM 文档 [`../ssot-spec/references/vdm/`](../ssot-spec/references/vdm/README.md)。
- 文字里提到规格元素，一律用双反引号写限定名，例如 ``` ``Run`Start`` ```。

## 五、交付

运行 `ssot check`，只用它排除解析、类型、布局与说明注释方面的错误，诊断按第三节处理。交付一张表：草稿里的每条约束写在哪个 `文件:行`、用了哪种写法；只写进「语义」的约束单独列出。

本块不给验证结论，设计交给 `ssot-verify` 验证。验证报出的问题，回到本块或 `ssot-draft` 修改。

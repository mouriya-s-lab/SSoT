# ssot-draft-requirement：为一条需求定落点

`scope` 是一个需求 id，或 `ssot-migrate-read` 交出的一个区域的需求摘录（那时对其中每条需求各做一遍）。本叶子不写任何载体的正文：它只决定需求由哪里兑现，并在落点元素上写下 `req`。

## 五项

| 项 | 内容 |
|---|---|
| 可读 | 这条需求的原文；`structure/*.c4` 里元素的 fqn、种类、标题、描述、标签、metadata `req` 与关系；带 `#contract` 的元素的模块 `exports` 部分（只读签名）；`behavior/` 下的模块名与它们 import 的生成模块；`ssot:reader` 为本需求或本区域写下的文件 |
| 可改 | `structure/*.c4` 里：落点元素的 metadata `req`；承担某条领域性质的元素的描述里，追加这条领域性质与来源。不改元素、关系、视图与其他描述，不碰 `contract/`、`behavior/`、`.gen/` |
| 工具工作集 | `ssot gen <design>`；对每个落点元素所在的视图（它的父元素的视图）运行 `ssot check <design> --scope <视图>`；`ssot status <design>` 确认这条 `req` 不再没有落点 |
| 末尾评审 | 无：落点是否兑现需求，由落点切片的写作叶子在它们的末尾评审里判断（`ssot-verify-structure` 的 S108 等） |
| 向上修正 | 第四步列出的情形 |

## 一、论证与领域性质

需求说的是问题域里要成立的效果，规格只能约束本系统。两者之间隔着外部世界本身成立的事实：领域性质。先写出论证：本系统要守住的约束，加上哪些领域性质，合起来推出这条需求。论证只在本次调用里用来定落点，不落盘。

- **需求是可观察的结果。** 它写的是用户或外部系统看到什么，不是机器的功能清单（S58）。原文写成了功能清单时，问它要让谁观察到什么。
- **规格加领域性质推出需求**（S6）。推不出，就是缺约束或缺领域性质，补上缺的那一条。
- **领域性质是外部世界的事实，有来源**（S79），不冒充本系统保证的不变量（S34）：把“外部会怎样”写成不变式，系统要应对的情况就被写成了不可能发生。每条领域性质写进承担它的元素的描述，附来源。
- **隐含前提有位置**（S4）。属于软件的前提，要么由某个元素定义，要么是一个外部依赖；不属于软件的运行前提（服务器需要电力）不进入设计。
- **参与者只用自己知道的值。** 论证里每个参与者的每一步，只用它本来知道的值，或它前一步调用的连接交给它的结果；拿不到某个值，就是缺一个交出它的连接。
- **依据有来源**（S48）：外部事实、约束与质量要求都写出来源。

## 二、拆成三面，各指向一个落点

| 面 | 问什么 | 落点 |
|---|---|---|
| 结构 | 哪个元素承担这个职责？ | 一个元素的 fqn |
| 契约 | 哪个带 `#contract` 的元素的连接承诺这个结果？ | 一个带 `#contract` 的元素的 fqn |
| 次序 | 需求有没有跨连接的先后、窗口、停机或崩溃收束？ | 一个 Quint 模块名，或“无次序要求” |

- 落点按持有者定：连接的提供方无论服务哪个合法使用方都必须保证的，落在架构元素上；某项业务在连接之上加的条件、选择或组合，落在那个业务元素上。两者都有时，这条需求混着两件事：两面分别落点（S84、S110 的同一判据）。
- 业务判断所需的事实不够时，落点仍是业务元素，并在交付里写明它需要哪个连接多提供什么；不把业务判断落到架构上（S63）。
- 不属于本系统承诺的需求，不为它找落点、不为它扩张结构（S62）：在交付里写明它不属于本系统承诺及理由，交给用户。

## 三、写 `req`

在结构面与契约面的落点元素上，把需求 id 写进 metadata 的 `req`（写法见 `../ssot-write/references/structure.md` 的「八、依据、理由与需求」）。次序面不写进任何载体：在交付里写明它交给哪个 Quint 模块。运行第五项里的检查与 `ssot status`。

## 四、向上修正

- 落点元素还不存在：停止，写明 `{skill: ssot-write-level, scope: <应当容纳它的父元素的视图 id>, reason: …}`。新元素写好后，这条 `req` 仍没有落点，`ssot status` 会再派回本叶子。
- 落点元素存在、但不带 `#contract` 而契约面需要它：写明 `{skill: ssot-write-level, scope: <它的父元素的视图 id>, reason: …}`。
- 原有的某个 `req` 落错了元素：只改那个 `req`，并在交付里写明改动与理由。

## 五、交付

需求 id、论证的一句话摘要、三面的落点、写了 `req` 的元素与追加的领域性质、`check` 与 `status` 的结果，以及按次序列出的下一项前沿：先契约面 `{skill: ssot-write-contract, scope: <元素 fqn>, reason: 需求 <id>}`，再次序面 `{skill: ssot-write-behavior, scope: <模块名>, reason: 需求 <id>；契约落点 <元素 fqn，逗号分隔>}`（行为要求它用到的契约模块先没有错误）；需要新元素时只列第四步的那一项。

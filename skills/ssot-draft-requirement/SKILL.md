# ssot-draft-requirement：为一条需求定落点

`scope` 是一个需求 id（`REQ-<编号>`），或 `ssot-migrate-read` 交出的一个区域的需求摘录（那时对其中每条需求各做一遍）。本叶子不写任何载体：它只决定需求由哪里兑现，并把落点交给写作叶子；需求编号由写作叶子附在兑现它的定义上（`ssot` 总纲第二节「需求」）。

## 需求清单

需求清单是 `<design>/requirements.md`。每条需求一个列表项，以 `REQ-<编号>` 开头，后面是需求原文：

```markdown
- REQ-1 使用方停止一次运行后，这次运行不再产生新的运行项。
- REQ-2 ……
```

- **原文由用户给出。** 需求的文字来自用户：用户在对话里说的，或用户给的需求材料里原文明写的。模型只给它编号，不改写、不拆分、不合并、不补充原文，也不自己写出需求。
- **编号。** 新需求取清单里已有的最大编号加一，追加在末尾。已有的编号与原文不改。
- **用户给的需求还不在清单里时**，先把它原样追加进清单并编号，再对它做下面各步。
- **迁移来的摘录。** `scope` 是需求摘录时，摘录里标为“需求”的每一条按原样追加进清单并编号；标为“外部事实”或“约束”的不进清单，只在论证里用（第一步）。

## 五项

| 项 | 内容 |
|---|---|
| 可读 | `<design>/requirements.md`；`structure/*.c4` 里元素的 fqn、种类、标题、标签与关系；带 `#contract` 的元素的模块 `exports` 部分（只读签名）与已附着的需求编号；`behavior/` 下的模块名、它们 import 的生成模块与已附着的需求编号；`ssot:reader` 为本需求或本区域写下的文件 |
| 可改 | `<design>/requirements.md`：只追加新需求并编号（「需求清单」一节），不改已有条目。不改 `structure/`、`contract/`、`behavior/`、`.gen/` |
| 工具工作集 | `ssot status <design>`：确认交出落点之前这条需求确实没有落点 |
| 末尾评审 | 无：落点是否兑现需求，由写作叶子末尾的契约与行为评审判断（「需求落点」等） |
| 向上修正 | 第三步列出的情形 |

## 一、论证与领域性质

需求说的是问题域里要成立的效果，规格只能约束本系统。两者之间隔着外部世界本身成立的事实：领域性质。先写出论证：本系统要守住的约束，加上哪些领域性质，合起来推出这条需求。论证只在本次调用里用来定落点，不落盘。

- **需求是可观察的结果。** 它写的是用户或外部系统看到什么，不是机器的功能清单。原文写成了功能清单时，问它要让谁观察到什么。
- **规格加领域性质推出需求。** 推不出，就是缺约束或缺领域性质，补上缺的那一条。
- **领域性质是外部世界的事实，有来源**，不冒充本系统保证的不变量：把“外部会怎样”写成不变式，系统要应对的情况就被写成了不可能发生。契约要依赖某条领域性质时，把它与来源写进交给 `ssot-write-contract` 的 `reason`，由契约作者写在依赖它的占位旁的注释里。
- **隐含前提有位置。** 属于软件的前提，要么由某个元素定义，要么是一个外部依赖；不属于软件的运行前提（服务器需要电力）不进入设计。
- **参与者只用自己知道的值。** 论证里每个参与者的每一步，只用它本来知道的值，或它前一步调用的连接交给它的结果；拿不到某个值，就是缺一个交出它的连接。
- **依据有来源。** 外部事实、约束与质量要求都写出来源；它们只在论证里用，不写进任何载体的描述。

## 二、定落点

| 面 | 问什么 | 落点 |
|---|---|---|
| 契约 | 哪个底层元素的连接承诺这个结果？ | 一个没有子元素、带 `#contract` 的元素的 fqn |
| 次序 | 需求有没有跨连接的先后、窗口、停机或崩溃收束？ | 一个 Quint 模块名，或“无次序要求” |

每条需求至少有一面落点：只有契约与行为能兑现可观察的结果，结构不持有需求。

- 落点按持有者定：连接的提供方无论服务哪个合法使用方都必须保证的，落在架构元素上；某项业务在连接之上加的条件、选择或组合，落在那个业务元素上。两者都有时，这条需求混着两件事：两面分别落点。
- 业务判断所需的事实不够时，落点仍是业务元素，并在 `reason` 里写明它需要哪个连接多提供什么；不把业务判断落到架构上。
- 不属于本系统承诺的需求，不为它找落点、不为它扩张结构：在交付里写明它不属于本系统承诺及理由，交给用户。

## 三、向上修正

- 契约面的落点元素还不存在：停止，写明 `{skill: ssot-write-level, scope: <应当容纳它的父元素的视图 id；父元素还没有子元素、也就没有视图时为父元素的 fqn>, reason: 需求 <id> 需要一个承担 …… 的元素}`。
- 落点元素存在、但有子元素或不带 `#contract`：写明 `{skill: ssot-write-level, scope: <它的父元素的视图 id>, reason: 需求 <id> 的契约面落在 <fqn>，它需要成为带 #contract 的底层元素}`。
- 某条需求已附着在不兑现它的定义上：写明那个定义所在的写作叶子与 `scope`，`reason` 写明应改附到哪里。

## 四、交付

需求 id、论证的一句话摘要、两面的落点，以及按次序列出的下一项前沿：先契约面 `{skill: ssot-write-contract, scope: <元素 fqn>, reason: 需求 <id>：<要承诺的结果一句话>；领域性质：<如有，附来源>}`，再次序面 `{skill: ssot-write-behavior, scope: <模块名>, reason: 需求 <id>；契约落点 <元素 fqn，逗号分隔>}`（行为要求它用到的契约模块先没有错误）；需要新元素或新契约标记时只列第三步的那一项。

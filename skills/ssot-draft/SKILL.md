# ssot-draft：写 VDM 之前定下约束与归属

本块产出目标仓库的 `.tmp/ssot-draft/draft.yaml`。可读 `design/` 与用户明确提供的材料；不改 `design/`，不写 VDM；只运行 `ssot draft` 核对草稿。范围是用户这次指定的需求，不顺带设计整个系统。

第一次运行 `ssot draft` 时，工具把设计里每个元素当时的原文记进 `.tmp/ssot-draft/baseline.yaml`，作为本轮的起点：之后 `ssot-design` 只要求本轮新增、改动或删除的元素对应本轮草稿，没动过的旧元素不归本轮解释。所以开始本轮之前，`design/` 里不能有别的未完成改动；草稿期间也不改 `design/`，否则那些改动会被当成起点。

下面每一节对应 `draft.yaml` 的一个列表。`ssot draft <子命令> <仓库根>` 从需求材料与草稿里枚举每一项要判断的内容，缺判、槽位没填、取值不在范围内、引用找不到时报错（台账的共用规则见 `ssot` 总纲第四节）。工具只保证每一项都判了，判得对不对仍按本节的方法。

```yaml
materials: [request.md]                    # 需求材料，路径相对仓库根
requirements:                              # 每个需求块一条：ssot draft requirements 打印缺判的骨架
  - block: {path: request.md, heading: [需求], text: …}
    constraints: [C1]                      # 落到的约束
    excluded: []                           # 或第四节的条目
objects:
  - {id: O1, name: …, kind: execution, identity: …, residue: …}
relations:
  - {from: O1, to: O2, kind: points, note: …}
constraints:
  - id: C1
    object: O1
    varies: …          # 允许的变化
    invariant: …       # 不变的关系
    violation: …       # 违反情形
    not_promised: …    # 不作的承诺
    rerun: …           # 换跑法的回答
    deletion: …        # 删除的回答
    scope: …           # 范围的回答
    category: transition
    owner: {layer: architecture, holder: …}
excluded:
  - {id: X1, text: …, unaffected: …}
tradeoffs:
  - {id: D1, question: …, options: [甲, 乙], choice: 甲, basis: …, wrong_when: …}
```

## 〇、需求

`materials` 列出用户给的需求材料。`ssot draft requirements` 把材料按 Markdown 结构切成需求块（段落、列表项、表格行、代码块；标题作为上下文），每块要有一条记录，写出它落到哪些约束，或哪些第四节的条目。材料改动后，原来那块的记录成为孤儿，改后的块缺判：重新判这一块。

## 一、分清对象（`objects`、`relations`）

需求里的每个名词，先判定它指哪一种对象（`kind`）：

- **定义**（`definition`）：运行前写下，可被多次使用；
- **执行**（`execution`）：有开始和结束，每次各自独立；
- **事实**（`fact`）：执行留下、之后被读取的东西；
- **索引**（`index`）：只标识前三者中的某一个，说明它此刻代表什么。

判定方法：设想有两份内容完全相同的它，问它们是同一个还是两个，把回答写进 `identity`。两份相同的定义是同一个；两次输入相同的执行仍是两个。一个词落到两种对象上时，拆成两个对象分别命名，之后每条约束只写在其中一个上。

再对每个对象问：拿掉它组合的、指向的东西之后，它自己还剩内容吗？回答写进 `residue`。不剩的是组合或索引，约束写在它组合或指向的那个对象上。

对象之间的关系分三种记录（`relations.kind`），不混用：包含（`contains`，谁的开始与结束在谁之内）、指向（`points`，只标识，不对对方做任何事）、作用（`acts`，开始、停下、写入、读取）。指向不能当作作用。`ssot draft objects` 对既不被约束引用、也不在任何关系里的对象给出警告。

## 二、写出约束（`constraints`）

每条候选约束填五项：

1. **约束对象**（`object`）：第一节判定出的哪个对象；
2. **允许的变化**（`varies`）：哪些值、结果、参与者、先后可以不同；
3. **不变的关系**（`invariant`）：上面的变化发生之后，仍必须成立的关系；
4. **违反情形**（`violation`）：需求不允许出现的一个状态或一次调用结果；它违反哪条需求，由第〇节的需求块落到它来表明；
5. **不作的承诺**（`not_promised`）：比这条更强、需求却没有要求的约束。

填完后按次序做三项判定，把回答写进对应字段：

- **换跑法（`rerun`）：** 改变实现、调用先后，或增加一个合法的使用场景，这条约束是否必须跟着改？必须改，它写的是现在怎样跑，不是约束，移到第四节。
- **删除（`deletion`）：** 去掉这条约束，能否出现违反情形？不能，它多余，删掉。
- **范围（`scope`）：** 这条约束是否把第一节里本应分开的对象当成了一个，例如把多次执行当成同一次？是，就过强：收回到正确的对象上，把更强的说法记进 `not_promised`。

最后标出约束的类别（`category`），供落地时选写法：任何时刻都成立的关系（`invariant`）、一次调用的准入条件（`admission`）、一次调用前后的关系（`transition`）、生命周期的先后（`lifecycle`）。需求关心的失败结局（调用方要区分的结果、失败时哪些东西不变）是 `transition`；只有需求要求失败之后按某种次序恢复，或要求生命周期中断时怎样收尾，才另写一条 `lifecycle` 约束。不为了让落地时有场景而把失败写成 `lifecycle`。本块不选 VDM 关键字。

`ssot draft constraints` 核对五项与三项判定都有回答、对象存在、类别在范围内，并对没有任何需求块落到的约束报错：它没有出处。

## 三、定归属（`owner`）

每条约束问两个问题：

- **连接的提供方无论服务哪个合法使用方，都必须保证它吗？** 是，由架构持有（`layer: architecture`），`holder` 写明是哪个连接。
- **它是某项业务为了自己的目的，在连接之上加的条件、选择或组合吗？** 是，由那个业务单元持有（`layer: business`），`holder` 写业务单元名。

两个都答“是”，说明一条里混着两件事：拆成提供方保证的部分和业务添加的部分，写成两条约束，分别归属。

下面这些理由不能改变归属。遇到时回到上面两个问题；业务做判定所需的事实拿不到，就改连接要提供的内容，不搬判定：

- 事实存放在某个模块里：持有事实，不等于持有基于这些事实的判定；
- 业务没有 `state`；
- 架构不能导入业务；
- 写成某个操作的 `pre` 更方便；
- 多项业务都用它：业务单元之间经导出的连接共用。

用户这次只要求设计架构时，业务持有的约束照样列出，标明归哪个业务，只是不展开。

## 四、不进 VDM 的内容（`excluded`）

列出被“换跑法”移出的内容，以及需求提到、但不约束任何对象之间关系的处理步骤。每条在 `unaffected` 写一句：它怎样变化，第二节的约束仍全部成立。

## 五、取舍（`tradeoffs`）

材料决定不了的语义或归属，列出可选项（`options`），自己选定（`choice`），写明依据（`basis`），以及在什么情况下这个选择是错的（`wrong_when`）。只有选项会改变用户的要求、材料又无法决定时，才问用户。旧文档与既有设计只用来理解对象的含义，不照搬其中的模块、记录和处理步骤。

## 六、完成条件

`ssot draft status <仓库根>` 没有错误，警告逐条看过。它保证每个需求块都有去向，每条约束五项与三项判定都有回答、归属有答案。工具判断不了的一条由你核对：剩下的问题都是“写成哪种 VDM”，没有“这句话指什么”“由谁保证”。

满足之后交付草稿路径并停止，由 `ssot-design` 按草稿写设计。草稿不是验证结论；它与基线保留到 `ssot-verify` 的结论交付，那时与落点台账一起删除（验证台账另按 `ssot-verify` 的规则保留）。

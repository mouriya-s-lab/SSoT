# ssot-draft：对象、不变量与职责划分的草稿

本块产出待落地的设计草稿，不产出正式规格或验证结论。先确定设计要守住什么，再决定用什么 VDM 形式表达；架构与业务在本块一起划分，不先做一份包办所有需求的架构。

## 工作边界

- 以用户指定的需求或设计问题为范围，不顺带设计整个系统。读取用户明确提供的材料与相关 `design/` 文档；材料说明已有含义与约束，不把旧模块、字段或处理步骤直接当成新设计。
- 草稿写在目标仓库的 `.tmp/ssot-draft.md`；用户指定了其他草稿路径时使用该路径。草稿可以用文字、图和数学关系，不受正式规格的目录、命名、注释和编译要求限制。
- 不修改正式 `design/`，不生成 VDM 模块骨架，不运行 `ssot init`、`ssot module`、`ssot unit`、`ssot graph`、`ssot check`、VDMJ 或 `review.py`。不读取其他设计或审查子 skill 来继续执行下一块，也不派发 subagent。
- 草稿中的取舍由设计者负责。查得到的事实直接核实；缺少的事实明确标出，不能编成前提。只有不同选择会改变用户要求、且现有材料无法决定时才向用户提出具体问题。

## 一、先分清对象，再谈关系

从需求涉及的对象与观察者出发，说明每个对象是什么、由谁创建和维护、谁需要观察什么。存在生命周期时，指出它何时开始、何时结束、嵌套在哪个对象内；没有生命周期的定义或值，不为了套用模板给它造生命周期。

同一个词指向不同对象时先拆清含义。尤其不能混用一份定义、一次实际执行、执行留下的事实，以及指向它们的索引。画图时分别表达包含、指向与作用，不把指向当成持有或调用。

此时不按已有目录分配对象，也不先造 `state`、类型字段或操作名，再替它们寻找存在理由。对象只有在需求的某个观察视角下确实需要被区分时才展开。

## 二、确定相对于什么变化，什么关系不能变

**不变量不是对象不变化，而是在所规定的变化范围内，必须保持成立的关系。** 先说允许什么变化，再说这些变化不能破坏什么；不能只写“所有合法状态都满足”，却不说明哪些情形应被排除。

对每条候选约束，在相关对象旁说明：

- **适用范围：** 约束哪个对象、哪段生命周期或哪条连接，依赖什么前提。
- **允许变化：** 哪些值、执行结果、参与者或实现做法可以不同。
- **保持的关系：** 这些变化发生时，哪些关系仍必须成立；破坏它会违反哪项需求或改变哪个对象的含义。
- **不作出的承诺：** 哪些看似更强的限制并非需求要求，不能顺手加入。

例如，“一次执行只交付一个最终结论”不能改成“同一声明和输入在所有执行中只能得到一个结论”。后一种约束把独立执行混成同一个对象，并额外承诺了结果确定性。需要先分清约束的是定义还是执行，再选择形式。

区分状态上始终成立的关系、一次调用的准入条件、变化前后的关系，以及生命周期的先后要求；不要把所有承诺都塞进一个 `inv`。本阶段先确定含义，不决定把句子翻译成哪个 VDM 关键字。

一条正确的执行路径只说明该路径没有破坏约束，不能代替约束本身。给对象取了名字、给模块写了导入列表，也不自动证明存在所声称的运行期隔离或访问限制。

## 三、同时划分架构与业务

围绕上一步的关系确定谁提供连接、谁消费连接、谁持有规则：

- **架构连接的承诺：** 提供方对不同合法使用方都要兑现的含义、边界和不变量。
- **业务单元的承诺：** 某项需求如何在这些连接上成立；业务自己持有的判定、选择和组合关系。
- **实现做法：** 换一种做法仍能兑现上述承诺的内部步骤，不进入设计约束。

业务也有维持设计形状的不变量，不是剩余细节的收容处。用户只要求讨论架构时，可以不展开业务内部，但必须指出由业务承担的职责，不能把它吸收到架构里凑完整。

**事实的持有者不因此拥有针对事实的一切判定。** 业务需要源头事实时，经连接取得事实并作自己的判定；同一规则被多个业务使用，也不自动成为架构规则，业务单元可以经导出连接共用它。

不得因为业务没有 `state`、架构不能导入业务、某个条件放在 `pre` 里更方便，或检查器可能报告未使用定义，就移动规则、合并对象或新增模块。遇到这种困难，重新检查连接究竟应当提供什么，而不是优先保住已选的表达方式。

## 四、形成草稿并交付

草稿按内容组织，至少让后续设计者能找到：

1. 本次要满足的需求、已有事实与尚缺的依据。
2. 对象及其关系，需要时附图；架构与业务各承担什么。
3. 候选不变量与其他契约：适用范围、允许变化、保持的关系及不作出的承诺。
4. 需要展开与有意不展开的部分，以及不展开是否妨碍表达必要的约束。
5. 尚未决定的语义或归属问题，以及可行选择与取舍理由。

**进入规格落地的条件：剩下的问题是“如何准确表达”，而不是“这句话指什么、为什么需要、由谁保证”。** 有未解决的语义或归属时，交付草稿并明确这些问题，不用 `token` 或未定义函数把它们藏成已经完成的设计。没有待决问题时直接说明，不为了填满栏目发明争议。

本块交付草稿路径和待决问题后停止，不自动进入规格落地或验证。草稿不是验证通过的答案：验证由独立审查任务执行，不能用讨论一致、作者的自查或“每条都有一个规格元素”代替验证。

后续落地若只是表达方式不合适，应更换表达；若必须改变对象、不变量或职责归属，应返回草稿块修订并说明原因，不能在落地中悄悄改掉设计。草稿中的当前结论被正式设计吸收后，删除这份临时草稿，不把它复制进附录或保留为另一套设计规则。

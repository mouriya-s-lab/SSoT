# ssot-iterate：日常迭代的增量准入

`ssot` 的起点是“随着代码落地，从宏观到微观逐步建模”，同时规定“在连接不变时可以替换的做法属于实现，不写进设计”。日常开发落地一段代码、演进一个模块或修复故障后，用本 skill 判断这次局部演进里**什么该进入 SSoT，什么只是盒子内部的实现变化、应当留在代码里不动**。

`scope` 是本次勘探的局部范围：一个容器或子系统的代码目录、一次提交或分支改动的涉及面，或一份局部设计说明。本 skill 以 `<design>` 已有 C4 基线为前提；面对尚未建立 C4 基线的整座存量项目或整批旧文档时，先用它的全景放大版 `ssot-migrate`。

| 项 | 内容 |
|---|---|
| 输入 | `scope`；局部材料路径；设计目录路径 |
| 可读 | 指定 `scope` 内的项目材料（代码目录、配置、局部文档）及 git 热点统计；`<design>/structure/*.c4` 与 `<design>/requirements.md`；本 skill、`ssot` 与 `ssot-c4`。不读 `contract/`、`behavior/`、`.gen/` |
| 可改 | 无 |
| 可运行 | `ssot hotspots <局部材料路径>`（由 `ssot:hotspot` 运行） |
| 输出 | 本次 `scope` 的增量准入报告（见「三、交付」） |
| 上抛 | 局部材料揭示现有 `structure/*.c4` 的上层划分（如父层容器边界或归属）与实际运行边界失真：在交付里指明它属于哪个父层视图 id 的 `ssot-write-level` |

## 派发

会话按 `ssot` 第九节：

1. 若 `scope` 在 git 代码仓库内，先派 `ssot:hotspot` 对该局部路径运行 `ssot hotspots`，从改动最多的文件与协同改动对反推问题热点、修复 commit 与关联 issue；
2. 派 `ssot:reader`，交给它本 skill 名、`scope`、局部材料路径、设计目录路径以及 `ssot:hotspot` 的热点溯源报告（如有）。

原样交付准入报告，再按交付末尾指明的下游 `{skill, scope, reason}` 依次接后续 skill。下面各节写给 `ssot:reader`（结合 `ssot:hotspot` 的溯源结果）。

## 一、怎样看局部材料

- **先用信息隐藏筛掉纯内部改动。** 只要元素对外的连接（谁向谁发起调用）、端口承诺的结果关系与数据不变量没有变，元素内部换算法、改数据库表字段、拆合内部类与函数、加减锁/缓存/重试策略，一律属于实现，SSoT 不动。
- **不拿实现代码反向改写契约。** 不读 `contract/` 与 `behavior/`，也不做“代码签名与 VDM 签名对比”。已有盒子的契约或接线只在有新的需求（进 `ssot-requirement`）或新的可证伪担心与热点 commit/issue 证据（进 `ssot-judge`）时，才由那两个 skill 决定是否更新。
- **用 commit/issue 热点区分真担心与空想担心。** 不对着普通代码凭空猜测“万一并发会怎样”；结合 `ssot:hotspot` 找出的高频修改文件、协同改动对、反复修复的 commit 与关联 issue，识别哪些边界真正在反复出问题。
- **区分对外承诺与具体补丁做法。** 代码或热点 commit 里靠锁、状态枚举、定时轮询或补偿任务试图防御的问题，不要把机制本身带进报告，而是还原成：“拿掉这套补丁机制后，连接上会观察到什么错误结果”。

## 二、筛成四个增量桶

对照 `<design>/structure/*.c4` 与 `<design>/requirements.md`，按 `ssot` 第二至四节与 `ssot-c4` 的标准，把本次 `scope` 的内容分流进四个桶（某桶为空时写“无”）：

1. **C4 结构变更（供 `ssot-write-level` / `ssot-write-deploy`）**
   - 本次新增、删除或调整职责/关系的 `actor`、`#external` 外部系统、`container`、`store`、跨元素调用（`->`）或部署节点；
   - 或某个已有 `container` 内部复杂到读图人必须看清功能块划分，确需展开直接子 `component`（默认不拆 `component`；此处不标 `#contract`）。
   - 每项写明归属的视图 id（或需新建视图的父元素 fqn）。
2. **新增系统级需求与领域性质（供 `ssot-requirement`）**
   - 材料里明确写出的、`<design>/requirements.md` 尚未收录的系统对外可观察要求：一条一项，用原文的话摘录并附出处；句子里夹带的表名、字段、格式、技术选型与具体做法删去（删节处写 `……`），只有原文把某个格式或数值本身当成外部硬要求时才保留；
   - 论证该需求所需的外部世界事实（领域性质，附出处，不冒充本系统保证的不变量）。
3. **新增候选担心与热点溯源（供 `ssot-judge`）**
   - 本次范围内真正存在跨进程异步交错、进程崩溃重启后失步、晚到/重入请求、或多方并发破坏权威事实源头的位置（尤其是 `ssot:hotspot` 反推出反复发生修复 commit 与 issue 的问题热点）；
   - 每项只写事实，不替 `ssot-judge` 抢先定 VDM/Quint 落点：
     - **位置：** 对应 `<design>/structure/*.c4` 中的元素 fqn 或两端元素 fqn 组成的连接（属于第一桶拟增元素的，写拟增元素 fqn）；
     - **具体担心：** 一句可以被证伪的话；
     - **热点 → Commit → Issue 溯源依据：** 支撑该担心的改动热点文件、关键修复 commit（短 hash 与修复主题）及关联 issue/PR（`#编号` 与故障现象摘要），以及它们揭示的故障或交错环境（进程崩溃重启、在途请求乱序晚到、并发重入等），不带表字段、锁、状态码或调用栈；
     - **现有定位手段：** C4 的边界与普通的编译检查能否直接定位它。
4. **留在代码里的实现部分（SSoT 不动）**
   - 明确列出本次看过但连接与承诺未变的内部重构、标准 CRUD、普通业务规则、表字段/DTO 改动、状态机进度枚举、锁/缓存/重试调整，以及虽改动次数多但只是常规功能堆叠的伪热点，一句话说明为什么不进入前三桶。

## 三、交付

按下面五项交付，不写任何文件：

1. **勘探范围与未决问题：** 实际读过的路径范围、热点统计概览，以及材料中冲突或未覆盖、需使用者拍板的问题；
2. **C4 结构变更：** 第一桶的逐项事实，每项标明应交给 `ssot-write-level`（或 `ssot-write-deploy`）及哪个视图 `scope`；
3. **待收需求与领域性质：** 第二桶的逐条摘录与出处（应交给 `ssot-requirement`）；
4. **候选担心与热点溯源：** 第三桶的逐项列表，每项标明应交给 `ssot-judge` 及对应的位置 `scope`；
5. **留在代码里的实现部分：** 第四桶的归类说明。前三个桶均为空时，结论写明“本次迭代属连接与承诺不变的内部实现演进，SSoT 无需改动”。

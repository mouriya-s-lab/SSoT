# ssot-judge：一个位置要不要往下写

准则在 `ssot` 第三节，本 skill 只给步骤与交付格式，不另立准则。

| 项 | 内容 |
|---|---|
| 输入 | 一个位置（元素 fqn，或两端元素 fqn 组成的一条连接），或 `ssot-iterate` / `ssot:hotspot` 交出的一项候选担心与热点 commit/issue 溯源 |
| 可读 | `structure/*.c4` 里元素的 fqn、种类、标题、描述、标签与关系；`ssot render` 的 C4 图；已有契约模块的 `exports` 与已附着的需求编号；`behavior/` 下的模块名与它接进来的契约模块；`requirements.md`；`ssot:hotspot` 交回的热点溯源报告 |
| 可改 | 无 |
| 可运行 | `ssot render <design>` |
| 输出 | 一份判断（见「交付」） |
| 上抛 | 位置本身在结构里不存在或放错了层：交回这个事实，给 `ssot-write-level` 与那一层的视图 id |

面对存量代码仓库中的位置、且输入里还没有该位置的 `ssot:hotspot` 热点溯源报告时，先按 `ssot` 第九节派 `ssot:hotspot` 对该位置对应的代码路径运行 `ssot hotspots`，拿到「改动最多的文件 → 关键修复 commit → 关联 issue」溯源结果后再往下做。

## 一、定位

看渲染图上这个位置：它是哪个框或哪个箭头，负责什么，与谁相连。担心或热点涉及一段跨连接行为时，找出这段行为经过哪些框与箭头。

## 二、回答三问

逐条写出答案，写不出就停在第一个答不出的地方：

1. **具体的担心。** 写出一句可以被证伪的话：“晚到的 reserve 在订单项释放之后仍被接纳锁库”“同一个订单项的结算结局被写下两次”。存量位置附上热点溯源依据（哪些高频修复文件、哪些 commit 与 issue 反推出这一担心；若热点分析表明该处虽改动多但只是常规 CRUD 扩展，直接停在此处）。泛泛的“这里很复杂”“可能有并发问题”不算。
2. **C4 与编译检查够不够。** 只靠图上的边界、普通的类型检查与常规测试，能定位它吗？能，就停在原处，交付里写明靠什么定位。
3. **模型会揭露什么。** 往下写一层后，哪一个错误的盒子（`post` 允许了不该允许的结果）或错误的接线（两个盒子以不该有的先后交错）会被检查发现？写不出这个错误的样子，就不往下写。

## 三、定落点与精度

三问都答得出时：

- 担心只关于一个底层元素的端口承诺（数据上的前后关系）：落点是这个元素的 VDM 盒子。它还不是没有子元素、带 `#contract` 的元素时，先上抛给 `ssot-write-level`，`reason` 写明它要成为带 `#contract` 的底层元素。
- 担心关于几个元素之间的先后、交错、崩溃或停机之后的收束：落点是一张 Quint 接线图。写出它真正要调用的契约端口，以及只在接线里出现的行为一侧盒子（进程、在途请求、环境）。参与接线不等于要有 VDM 盒子：还没有盒子的元素，只有它自己的端口承诺也答得出三问时，才另落一个 VDM 盒子；否则它在接线里是行为一侧的盒子。
- 精度按这个担心与热点 commit/issue 暴露的故障边界决定（`ssot` 第三节表格）：写明哪些端口只写签名与 `token`、哪些地方要精确到什么性质，以及要接进来的环境盒子（只接触发该担心或热点 commit/issue 证实发生过的崩溃、乱序、重入）。

## 交付

- 位置与它在图上的样子；
- 三问的回答（停在哪一问，或三问全部的答案，含热点 commit/issue 溯源依据）；
- 结论：停在原处，或落点（元素 fqn 的 VDM 盒子 / Quint 模块名与接进来的盒子）与精度；
- 需要先做的上抛（如有）。

判断不落盘；被采纳时，它体现为接下来写下的载体。

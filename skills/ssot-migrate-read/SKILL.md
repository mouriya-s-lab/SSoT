# ssot-migrate-read：代读旧文档的一个区域

旧设计文档里绝大多数内容是字段、记录形状、处理先后、校验与错误处理这些实现细节。直接读它写设计，会被细节带着走。所以迁移不搬运原文：旧文档由 `ssot:reader` 代读，只把概念与原文明说的需求交出来，之后由 `ssot-requirement` 逐条收下并判断，设计照常按 `ssot` 写。你不读旧文档，只读代读者写下的文件。

`scope` 是旧文档的一个区域：一个概念所在的那一节，或一个没有标题的文件。`.tmp/ssot-migrate/regions.md` 还不存在时，先做第一步。

| 项 | 内容 |
|---|---|
| 输入 | 旧文档的位置与迁移范围（用户的原话）；一个区域 |
| 可读 | 代读者在 `.tmp/ssot-migrate/` 下写的文件；`structure/*.c4` 里元素的 fqn 与标题。不读旧文档，不读 `contract/`、`behavior/` |
| 可改 | 无。只有代读者写 `.tmp/ssot-migrate/` |
| 可运行 | 无 |
| 输出 | 区域编号、两个文件的路径、摘录里的需求条数与外部事实条数；接下来交给 `ssot-requirement`，输入是 `.tmp/ssot-migrate/<区域编号>/requirements.md` |
| 上抛 | 不适用。代读者交出的概念与现有设计冲突时，不在这里判断，原样交给 `ssot-requirement` |

## 一、区域清单（只在第一次做）

按 `ssot` 第九节派 `ssot:reader`（`isolated: false`，留着供追问），只告诉它：旧文档的位置、迁移的范围、要它先写区域清单 `.tmp/ssot-migrate/regions.md`：每个区域一行，写文件、标题与一句话的主题，不写内容。

## 二、代读一个区域

本会话里派出的代读者还在，就给它发消息；不在，就按第一步新派一个，只告诉它旧文档的位置、`regions.md` 与要读的区域。消息里给出区域编号与输出目录 `.tmp/ssot-migrate/<区域编号>/`。它写两个文件：

- `concepts.md`：概念备忘。每个对象是什么、从哪来或为什么需要、守住什么、和谁什么关系，附出处与读到的范围；
- `requirements.md`：原文明确写出的需求、外部事实与约束，一条一项，原文摘录并附出处，标明是需求、外部事实还是约束。

只读这两个文件，不读代读者的会话记录。有概念问题时追问它（它写成同目录下的 `reply-<编号>.md`）：只问某个对象是什么、为什么需要、和谁什么关系、原文有没有作某个划分。不问细节，不问“这样划分对吗”。它说“原文没有”时，看它写明的读到的范围；没读到的不能当作没有。

## 三、交接与结束

按「输出」交付。外部事实与约束只在 `ssot-requirement` 的论证里用，不写进任何载体的描述。旧文档里的约束、模块划分与做法只是旧设计的样子：不搬进结构，不成为任何元素的描述或依据。

`regions.md` 里每个区域都有输出目录、且其中的需求都已经由 `ssot-requirement` 收下，迁移就结束；旧文档的去留由用户决定。本次调用结束前，删掉拷入项目的 `.omp/agents/ssot-reader.md`。

# ssot-migrate：存量项目的全景准入分流

日常开发中，对单个模块或一次改动用 `ssot-iterate` 判断哪些增量进入 SSoT。把整座存量项目或整批旧设计迁入 SSoT，是 `ssot-iterate` 在**全项目尺度上的放大版**：存量项目体量大且还没有 C4 基线图，不能把全部代码或文档一股脑塞进一次局部勘探。因此 `ssot-migrate` 只做**全局第一刀**——

1. 摸清全系统的宏观运行拓扑，供 `ssot-write-level` / `ssot-write-deploy` 先把顶层（`index`）、容器层与部署视图画出来；
2. 对照容器与子系统边界，结合全仓 git 改动热点分析（哪个文件/模块代码改得最多、哪些文件总在同一修复 commit 中协同修改、反推到哪些修复 commit 与关联 issue），**当场把低修复密度或纯功能堆叠的标准 CRUD、单纯转发与常规业务区域判为“停在 C4 框与箭头，不再下探”**，只挑出少数真正握有核心数据权威且在 commit/issue 历史中反复暴露出并发/崩溃/不变量隐患的**重点问题热点区域**；
3. 等全局 C4 基线图立稳并通过结构盲审后，对挑出的重点区域**按热点严重度逐个接 `ssot-iterate`**，进入与日常迭代完全一致的局部深入流程。

`scope` 是本次迁移的顶层目标：整个项目仓库、一批旧设计文档，或一个尚未建入 SSoT 的大型子系统。

| 项 | 内容 |
|---|---|
| 输入 | `scope`；存量材料路径（代码库根目录、部署配置、旧设计文档目录等）；设计目录路径（若已存在） |
| 可读 | 指定 `scope` 内的顶层材料（顶层目录结构、模块清单、构建与容器编排配置、进程入口、存储与通道配置、文档总览）及 `ssot hotspots` 全仓热点输出；`<design>/structure/*.c4` 与 `<design>/requirements.md`（若已存在）；本 skill、`ssot` 与 `ssot-c4`。不读局部业务实现代码，不读 `contract/`、`behavior/`、`.gen/` |
| 可改 | 无 |
| 可运行 | `ssot hotspots <存量材料路径>`（由 `ssot:hotspot` 运行） |
| 输出 | 全局 C4 基线事实、全局待收需求与基于热点溯源的区域分流表（见「三、交付」） |
| 上抛 | 存量材料揭示现有 `structure/*.c4` 的顶层划分与真实运行边界不符：在交付里指明它属于 `ssot-write-level`（`scope` 为 `index`） |

## 派发

会话按 `ssot` 第九节：

1. 若存量材料在 git 仓库内，先派 `ssot:hotspot` 对仓库运行 `ssot hotspots`，找出全仓改动最多的文件与模块、协同改动对，并反推到关键修复 commit 与关联 issue；
2. 派 `ssot:reader`，交给它本 skill 名、`scope`、存量材料路径、设计目录路径（若已存在），以及 `ssot:hotspot` 的全仓热点溯源报告（如有）。

原样交付它的全景分流结果，再按「先后来自输入」依次接 `ssot-write-level` / `ssot-write-deploy`、`ssot-requirement` 与重点区域队列里的 `ssot-iterate`。下面各节写给 `ssot:reader`（结合 `ssot:hotspot` 的全仓热点报告）。

## 一、怎样做全局勘探

- **只看骨架，不下探局部实现。** 勘探代码库时，只看顶层目录结构、模块/包清单、构建与容器编排配置、进程入口、数据库与消息通道配置、文档目录总览，以及 `ssot:hotspot` 的全仓热点统计；摸清有哪些独立运行单元、持久化存储源头、外部依赖与信任域即可，不在这一步读具体业务模块内部的代码或单章旧文档的细节。
- **按 C4 容器层级收束。** 全局基线只立到 `actor`、`system`（含 `#external`）、`container`、`store` 与 `deploymentNode`；不在全局迁移第一步拆分 `component`，也不标 `#contract`。单张数据库表归入所属的 `store`，不能单独运行的代码包归入所属的 `container`。
- **用 commit/issue 热点在区域粒度做初筛。** 对每个容器或业务区域结合 `ssot:hotspot` 的溯源链问一句：这里有没有高频修复 commit、跨边界协同修复或关联 issue 暴露出的跨进程交错、崩溃重启失步、多方并发写同一份权威事实？没有（改动少，或虽改动多但只是顺次增删标准 CRUD、普通页面、同步请求响应、单步转发），就直接归入“停在 C4，不再下探”。

## 二、筛成三个全局桶

1. **全局 C4 基线事实（供 `ssot-write-level` / `ssot-write-deploy`）**
   - **系统上下文（`index`）：** 顶层的 `actor`、本 `system`、直接交互的 `#external` 外部系统，以及它们之间的调用方向（`->` 与短动词短语）；
   - **容器层：** 本系统内全部 `container`（应用进程、转递通道）与 `store`（持久化事实源头），各自的 `technology`、一句话职责、同层兄弟的逻辑分组（`metadata group`）、业务标记（`#business`），以及容器之间、容器与外部之间的调用关系（`->`）；
   - **部署与信任边界（如有）：** 不同主机或信任域的 `deploymentNode`、节点内运行的容器/存储实例与信任边界标签（如 `#untrusted`）。
2. **全局系统级需求与领域性质（如有，供 `ssot-requirement`）**
   - 顶层总览文档中明确写出、横跨全系统的对外可观察要求（一条一项，原文摘录，删去夹带的表字段、格式与具体做法并标 `……`，附出处）及配套的领域性质；属于某个局部区域的需求留给该区域的 `ssot-iterate` 提取，不在这里展开。
3. **区域分流表（决定每个区域停在 C4 还是进入 `ssot-iterate`）**
   - **直接停在 C4 的区域（迁移到此结束）：** 列出所有属于标准范式、普通 CRUD、内部管理后台、单纯转发，或在 `ssot:hotspot` 中无修复热点（或仅为常规功能扩展）的容器/模块/旧文档章节，一句话写明职责与不再下探的理由；
   - **排入 `ssot-iterate` 的重点热点区域队列：** 列出少数真正需要下探局部材料的容器、子系统或旧文档区域；每项写出该区域的名称、对应的局部材料路径 `scope`、`ssot:hotspot` 反推出的「高频改动文件 → 关键修复 commit → 关联 issue」热点摘要及并发/崩溃/权威不变量线索，并按“核心事实源头优先、修复 commit 与 issue 密度最高的热点区优先”排定先后顺序。

## 三、交付

按下面四项交付，不写任何文件：

1. **勘探范围、全仓热点概览与未决问题：** 实际看过的顶层目录、配置与文档总览，`ssot:hotspot` 的全仓高频改动文件/模块与关联 issue 概览，以及需使用者拍板的系统边界问题；
2. **全局 C4 基线事实：** 第一桶的全部内容，按 `index`（交 `ssot-write-level`，`scope` 为 `index`）、容器视图（交 `ssot-write-level`，`scope` 为系统 fqn 或视图 id）、部署视图（交 `ssot-write-deploy`）排列；
3. **全局待收需求与领域性质：** 第二桶的逐条摘录与出处（交 `ssot-requirement`，无则写“无”）；
4. **区域分流表：** 第三桶中“直接停在 C4 的区域”清单，以及“排入 `ssot-iterate` 的重点热点区域队列”（每项标明待在全局 C4 基线立好后交给 `ssot-iterate` 的 `scope`、热点 commit/issue 依据与顺序）。

# ssot-requirement：收下一条需求

| 项 | 内容 |
|---|---|
| 输入 | 用户给的一条需求原文，或 `ssot-migrate-read` 交出的需求摘录路径（摘录里的每条各做一遍）；使用者说明的项目阶段 |
| 可读 | `requirements.md`；`ssot-judge` 的「可读」；`ssot:reader` 为本需求或本区域写下的文件 |
| 可改 | 只有 `requirements.md`：追加新需求并编号，不改已有条目 |
| 可运行 | `ssot render <design>` |
| 输出 | 需求 id、论证摘要、判断（与 `ssot-judge` 的交付相同） |
| 上抛 | 同 `ssot-judge` |

需求与判断在同一次调用里完成：判断不落盘，分开做会让一条已编号、未判断的需求在会话之间静默丢失。

## 一、编号

- **原文由用户给出。** 需求的文字来自用户：用户在对话里说的，或用户给的材料里原文明写的。只编号，不改写、不拆分、不合并、不补充原文，也不自己写出需求。
- **编号。** 取清单里已有的最大编号加一，追加在末尾：`- REQ-<编号> <原文>`。已有的编号与原文不改。
- **迁移来的摘录。** 摘录里标为“需求”的每一条按原样追加并编号；标为“外部事实”或“约束”的不进清单，只在论证里用。

## 二、论证与领域性质

需求说的是问题域里要成立的效果，规格只能约束本系统。两者之间隔着外部世界本身成立的事实：领域性质。先写出论证：本系统要守住的约束，加上哪些领域性质，合起来推出这条需求。论证只在本次调用里用，不落盘。

- **需求是可观察的结果。** 原文写成了功能清单时，问它要让谁观察到什么。
- **领域性质是外部世界的事实，有来源**，不冒充本系统保证的不变量。
- **隐含前提有位置。** 属于软件的前提，要么由某个元素定义，要么是一个外部依赖；不属于软件的运行前提（服务器需要电力）不进入设计。
- **参与者只用自己知道的值。** 论证里每个参与者的每一步，只用它本来知道的值，或它前一步调用的连接交给它的结果。

## 三、判断

按 `ssot-judge` 的一到三步做，结论是下面之一：

| 结论 | 含义 | 接下来 |
|---|---|---|
| 结构已回答 | 图上看得出它成立（例如“数据只经某个容器进出”是一条箭头） | 图上还看不出时，上抛给 `ssot-write-level` 与那一层的视图 id |
| 盒子兑现 | 一个底层元素的端口承诺 | 交给 `ssot-write-contract`，`reason` 写需求 id 与要承诺的结果 |
| 接线兑现 | 几个元素之间的先后、交错或收束 | 交给 `ssot-write-behavior`，`reason` 写需求 id、要接进来的盒子 |
| 不建模 | 标准范式、排错简单，或阶段还不支持 | 无；需求留在清单里 |
| 不属于本系统 | 本系统承诺不了 | 交付里写明理由，交给用户 |

不为一条需求扩张结构，也不为让它“有落点”而建模。

## 交付

需求 id、论证的一句话摘要、判断结论（含三问的回答、落点与精度），以及接下来要接的 skill 与 `reason`（如有）。

# ssot-review-arch：抽象逻辑与架构/业务边界审查

## 这个阶段解决什么问题

在检查任何局部 VDM 语法或函数细节之前，回答两个根本问题：
1. **这份 `design/` 到底在描述一个什么抽象模型？它的抽象逻辑是什么？**
2. **系统的架构模块与业务单元的边界、持有者归属、依赖方向和依据理由是否成立？**

---

## 硬禁令（违反任一条即审查失效）

1. **未写出系统的抽象逻辑前，严禁报任何问题。**
   不得跳过「关键动作 1」直接拿着审查清单逐行扫 VDM-SL、挑局部 `post` 写法或数某个类型被几个模块 import。
2. **本阶段聚焦整体架构与业务边界，不纠缠单行 VDM 语法与局部谓词细节。**
   按 `design/README.md` 的阅读次序阅读 `design/` 下的 `architecture/` 与 `business/` 文件，并结合 `ssot graph <design>` 进行审查。
3. **禁止“找茬 KPI”心态。**
   设计没有架构问题就如实说架构成立，严禁为了证明自己干活了而把正常的分层细化或实现脑补硬凑成“架构缺陷”。
4. **被用户追问时，严禁把思维错误包装成“措辞失误”，严禁无原则翻供或抓逃生窗口。**
   如果自己的判断是从存储/实例/实现出发而导致的误判，直接承认**审查方法错在哪里**，用正确模型重审全盘结论；严禁靠随机撤回几条来迎合，也严禁抓住一个改名小活去改文件、借机逃避还没审完的架构与业务问题。

## 关键动作 1（第零步门控）：还原系统的抽象逻辑

通读 `design/` 全部 `architecture/` 与 `business/` 文件后，**必须先不带批判地写出系统的抽象逻辑**。写不出以下五点，或者其中任何一点还要靠猜，说明还没读懂设计，禁止往下做缺陷判定：

1. **抽象边界（认什么、排除什么）：**
   系统把充满副作用的外部世界收敛成了什么核心抽象（例如：把外部进程/智能体执行收敛为“静态定义 + 绑定输入值 = 纯函数调用”，只承认经声明边界交出的闭合结局）？哪些外部现实（如进程内部未声明副作用、底层传输/文件锁、换一次物理执行会不会输出不同）被明确划在抽象边界之外？
2. **状态真源与投影关系：**
   系统中真正持有的核心状态/持久事实是什么？其余概念（如运行整体状态、已结算视图、时间轴与对比视图）是独立的可变状态，还是核心事实之上的纯函数投影？
3. **值与等价关系：**
   系统里的核心值代数是什么？用什么纯函数定义相等或等价（如两次调用何时算同一次调用）？这个等价关系在设计中起什么作用（是许可引用既往事实，还是全局唯一约束）？
4. **生命周期与锚点嵌套：**
   系统中有生命周期的对象有哪些？外层锚点与内层资源的开始、结束次序是如何嵌套的？
5. **按一般性分层的逻辑（上层立什么规律，下层怎样细化）：**
   每个 `architecture/` 模块立了什么最一般的结构与底线不变量？每个 `business/` 单元如何在这些底线规律之内做策略细化与跨连接编排？

## 关键动作 2：过五道假阳性筛子（防二极管与实现脑补）

对初步怀疑的任何“矛盾”“重复”或“缺失”，在定性为问题之前，必须逐一过下面五道筛子。凡命中的，一律属于审查者自己的误读，当场排除：

| 筛子 | 典型误判表现（反例） | 正确判据 |
|---|---|---|
| **1. 边界外脑补筛子** | “智能体/LLM 对同一次调用的输出本身不确定，重跑可能得出不同结果，所以按输入相等引用旧结果不成立” | **边界之外不存在。** 既然抽象边界已声明只承认经边界交出的结局、把调用定义为“定义身份 + 绑定值”，物理世界里“再跑一次会不会不同”在抽象模型中根本不存在，不得拿边界外的物理性质反推模型矛盾 |
| **2. 等价当身份筛子** | “`SameCall` 判两次调用相等，但派生运行对未消费的异常又产生了一条新的 `OwnCall`，导致同一次调用有两条执行事实，违反模型” | **等价是许可，不是全局唯一约束。** 区分架构的**状态不变量**（如“同一运行内每个位置至多一条记录”）与**等价判定函数**（给出跨运行能否采用既往结果的许可条件）。架构没有断言全局只能有一条执行记录；是否采用既往记录由持有该策略的业务单元决定 |
| **3. 一般与细化筛子（防字面 Diff）** | “`Facts` 不变量允许复用任何非 `<Stopped>` 的已结束调用，而 `Derivation` 只允许复用正常产出或被接住的异常，两边规则重复且宽严不一致”；“架构 `Position.rounds` 支持多层循环，而 `Workflow` 只允许单层循环，两边不一致” | **下层比上层窄是细化，不是冲突。** 架构给出最一般的坐标和事实完整性底线（如 `<Stopped>` 未得出业务结论，不能当作已结算结果），业务单元在底线之上取更窄的子集，这是正常的分层细化。**只有业务需要而架构表达不了，或业务违反了架构断言的不变量，才是冲突** |
| **4. 存储与实例思维筛子** | “介入编辑没有地方持久保存，`Facts` 缺一个保存编辑的连接”；“`Facts` 不需要知道 `InteractionFact` 的变体，只存一条不透明序列 `seq of token` 就够了”；把“复用/重跑”理解成从旧执行实例里拿状态或把同一个实例再跑一遍 | **从函数、值与类型可见性出发，不从存储或实例出发。** 问“一次运行/调用由哪些值决定、哪个模块需要构造和模式匹配该类型”，绝不问“存在哪张表里”。（注：架构不能反向 import 业务；若架构把跨模块共享的事件类型抹成 `token`，业务模块将既无法构造变体、也无法在读取后分支匹配！） |
| **5. 契约外调用筛子** | “`PublishEnd` 的 `post` 要求 `ending = nil`，却没有为已经结束的运行项定义 `<AlreadyEnded>` 返回结局” | **契约之外不是缺失结局。** 写在 `pre`/`post` 里的前置状态条件是该连接的准入契约，调用方在契约之外调用属于违规，不必列为返回值分支；只有调用方在遵守契约的前提下仍必须区分处理的外部结果（如 `<Unavailable>`、`<Unknown>`），才列为结局 |

## 关键动作 3：执行架构与业务边界审查

筛掉假阳性后，按以下五个维度审查架构与业务是否正确：

### 1. 架构模块划分与依赖方向
- 运行 `ssot graph <design>`，对照各 `README.md` 的负责范围：
  - 只看模块图与负责范围，能否清晰回答架构三问（由什么组成、用什么组成、谁在谁里面）？
  - 依赖方向是否严格满足：`architecture/*` 零引用 `business/*`、父模块零引用子模块、模块目录间无环？
  - 模块是否按**抽象**（对外陈述连接、对内隐藏决定）划分，而非按篇幅或执行步骤切分？
  - 适用的包含关系（同进程、同部署、同信任范围、同存续期）是否已在 `README.md`「语义」中写明？

### 2. 架构纯度与业务抽象度
- **架构纯度：** `architecture/` 中是否混入了只服务于单一业务单元的策略规则，或连接不变即可替换的实现做法（如词法语法、序列化字节序、文件锁、轮询队列、细分报错文案）？
- **业务抽象度：** `business/` 各单元是否只写“怎样经架构连接运行与组合、两个实现必须得出同一结果的确定性判定、走通需求的场景”，还是把常变的业务内容本身或可替换的具体算法过程塞进了设计？

### 3. 视角与持有者归属
- 每样东西（类型、状态、不变量）是否定义在真正持有它的模块，且**全局只展开一次**？
- 观察者需要分支匹配或读字段的才带 `struct` 导出，不需要内部结构的身份/凭据是否保持 `token` 且不带 `struct` 导出？
- 每个行为是否写在做出行为的一方？每条业务策略的细节是否只在该策略的持有者模块展开？
- 属于软件一部分的隐含前提，在模块中是否都能通过 `imports` 找到持有者定义？不属于软件的前提是否未写进设计？

### 4. 连接面与状态不变量
- 共享同一份 `state` 的一组操作，是否真的共享并维护同一条状态不变量 `inv`？
- 状态是否保持最小化（只保留源头事实，不放可由纯函数投影算出的冗余状态或缓存字段）？

### 5. 依据与理由闭环
- 每条「依据」是否都是会改变设计的外部事实、约束、系统级需求或质量要求，写明了“来源”并接“所以……”说明它让设计多了或少了什么？
- 每个改变架构或业务形状的决定是否在「为什么」中有理由支撑（引用依据或需求），并在存在可信替代时写明了为什么不选替代方案？

## 输出规范与门控

本阶段输出必须严格包含两部分：

1. **系统抽象逻辑还原**：先用一段话或列表写出「关键动作 1」还原出的五要素（抽象边界、真源与投影、值与等价、生命周期嵌套、一般与细化分层），证明审查建立在正确的抽象模型之上。
2. **架构与业务边界裁决**：
   - 明确列出成立的架构与业务设计决定；
   - 对发现的真实边界问题，每条写明**它挑战的是哪条抽象规律、哪条依赖/持有者原则或哪条依据**，并给出精确的 `文件:行号` 证据；
   - 若某处设计取舍取决于作者的领域意图（例如某个共享代数放在架构层还是提升某个模块），**写成待向作者确认的开放问题，严禁写成非黑即白的“错误/撤回”判决**。

本阶段确认架构与业务边界清楚后，进入阶段二 **`ssot-review-flow`**。

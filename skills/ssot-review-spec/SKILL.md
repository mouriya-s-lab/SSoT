# ssot-review-spec：形式化规格严密性、证明义务与字面用词审查

## 这个阶段解决什么问题

在架构边界（`ssot-review-arch`）和业务值流转与场景走通（`ssot-review-flow`）审查完毕后，对 `design/` 进行**形式化规格严密性**与**表述卫生**的最终把关：
1. 机械检查（`ssot check`）与语义反模式模型审查（`review.py`）是否全部零违规？
2. QuickCheck 标为“未定/未评估”的证明义务是否真的成立？
3. 每个 `--` 说明注释里写的承诺，是否都诚实地写进了 `inv`、`pre`、`post` 谓词，没有用伪装重言式糊弄类型检查器？
4. 规格的标识符和说明注释里，是否有按字面意思读会把读者误导到“面向对象实例、缓存、存储或重复执行”的用词？

---

## 关键动作 1：运行 `ssot check` 与 `jev` 模型审查

1. 在终端运行确定性检查与 QuickCheck：
   ```sh
   ssot check <design>
   ```
   确认 8 个阶段（`layout`、`parse`、`structure`、`antipattern`、`form`、`prose`、`typecheck`、`quickcheck`）全部通过，退出码为 0，且无 Warning。
2. 在 omp 的 Python `eval` 中运行 `jev` 语义反模式审查：
   ```python
   %load skill://ssot/scripts/review.py
   findings = await review("/path/to/repo/design")
   ```
   确认 12 类语义反模式（`stringly`、`bool_stack`、`reasons`、`comment_shape`、`impl_body`、`registry`、`simulation`、`business_in_arch`、`prose_restates`、`coined`、`basis`、`figure_code`）检出数为 0。若有检出，逐条核对并修正。

## 关键动作 2：逐条裁决 QuickCheck 未定证明义务

`ssot check` 通过只代表 QuickCheck 在有限随机样本上没有撞出反例，输出中列出的 `未定`（MAYBE）或 `未评估`（UNCHECKED）证明义务必须逐条人工核实：

- **常见类型：**
  - **Subtype obligation**：分支里把并类型传给只接收某一个子类型的参数（如 `if found <> <Absent> then Finish(found)`）；
  - **Map / Sequence apply obligation**：访问 `m(k)` 或 `s(i)` 时，`k in set dom m` 或 `i in set inds s` 是否由前置守卫保证；
  - **State invariant obligation**：隐式操作的 `post` 允许的每一种后置状态，是否都保持 `state ... inv` 成立；
  - **Recursive measure / totality obligation**：递归纯函数的 `measure` 在每次递归调用时是否严格递减。
- **裁决标准：**
  逐条写出该义务所在行号、它要求什么条件、上下文里哪一行守卫或哪条不变量保证了它成立；如果上下文**并不能保证**它成立（例如漏了 `pre` 或 `dom` 守卫），将其列为规格缺陷。

## 关键动作 3：核对说明承诺与谓词的一致性（揪出伪装约束）

`ssot check` 的 AST 反模式阶段能抓出直接的 `post true`、`r = r`、`P or not P`，但抓不出更隐蔽的“说明写得很满、谓词实际放水”。逐个模块核查：

1. **伪装重言式（Disguised Tautology）：**
   - 检查是否有为了消除 VDMJ `Warning 5000`（参数未使用）而塞进 `post` 的恒真废话，例如：
     ```vdm
     -- 反例：用 = {} or <> {} 伪装使用了 placements 参数，实际未做任何约束
     and (placements = {} or placements <> {})
     ```
   - 如果该操作确实不需要在抽象状态里记录该参数，思考是状態建模漏了分量，还是该参数根本不该出现在这个连接点上；绝不用恒真式欺骗检查器。
2. **说明承诺未落入谓词：**
   - 对照每个类型、状态、函数、操作的 `--` 说明注释与它的 `inv`/`pre`/`post`：
     - 说明里写的每一句“必须 / 只 / 幂等 / 已关闭时必拒绝 / 保持一致”，在谓词里是否有对应的合取项？
     - 例如：说明写“关闭后仍可读取关闭时刻固化的最终快照”，但 `ObserveRoot` 的 `post` 允許在关闭前任意时刻固化一份快照并在关闭后继续返回那份旧快照——这就是谓词比说明承诺更弱。
3. **帧条件（Frame Conditions）与悬空 `ext`：**
   - 隐式操作的 `ext rd/wr` 列表里，是否有根本没在 `pre`/`post` 中出现的冗余状态分量？
   - 在 `ext wr x wr y` 的每个 `or` 分支（尤其是失败或幂等分支）中，是否明确写全了未改变分量的保持条件（`x = x~ and y = y~`）？在 VDM-SL 中，`ext wr x` 的某个分支如果不写 `x = x~`，意味着该分支允许 `x` 变成任意满足状态不变量的值！

## 关键动作 4：字面误读与词汇卫生审查

为什么字面误读是真问题：如果规格里的类型名、操作名、函数名或 `--` 说明注释按字面意思读，会把读者引向**面向对象实例、指针引用、缓存复用、原地重跑或数据库存储**，读者（包括后续维护或审查的 AI）就会按字面建错心智模型。

扫描 `design/` 下的全部标识符、`--` 说明注释与 `README.md` 正文，重点排查以下四类误导性表述：

| 误导类别 | 典型字面用词 | 字面会让人误解成什么 | 抽象模型中的真实含义 |
|---|---|---|---|
| **1. 缓存/拷贝式动作词** | “复用”“结果复用记录”“复制位置”（如 `ReusedCall`、`PublishReuse`、`ReuseDecision`） | 从旧执行实例里拿走结果、拷贝状态或复用执行环境 | 派生运行在该位置的调用（定义 + 绑定值）与既往已发布结局的那次调用满足 `SameCall` 等价，因此就是同一次调用，直接引用那条已发布事实 |
| **2. 原地重复执行词** | “重跑”“从头执行”“介入重跑”（如 `RerunDecision`） | 把同一个调用实例再执行第二遍 | 该位置的输入被编辑、或上游结局改变、或源运行未得出有效业务结论，因此在派生运行中作为一次新的自有调用执行 |
| **3. 指针/有状态实例词** | “指向某个实例”“重附着到闭包实例”“对象”“句柄” | 内存中存在一个可变对象，拿着指针连回去改它的状态 | 按持久身份 `CallId` 幂等取得同一个闭包边界凭据，或通过 `CallId` 指认哪一条已发布的不可变事实 |
| **4. 存储与实现理由词** | “持久保存”“不存储结构副本”“制造存储中的双源同步负担”“不作为可变字段存储” | 用数据库表结构、内存字段或写盘成本来论证设计 | 这是源头事实与纯函数投影的问题（事实是唯一状态，其余皆为事实上的纯函数，单一展开避免多重解释），设计里不谈怎么存储 |

### 修正规则（要么改词，要么加解释）

发现字面误读用词时，严格按以下二选一处理：
1. **改词（首选）：** 在持有该元素的模块把误导性的标识符或措辞改为准确反映抽象语义的名字，并**在同一次改动中同步更新所有 `imports`、`exports`、调用点及正文里的双反引号引用**，确保 `ssot check` 零断口。
2. **在持有处加解释：** 如果保留原标识符，必须在该元素定义处的 **`--` 说明注释**（或所属模块 `README.md` 的「语义」）里直接点破字面歧义，写明它在函数与值抽象中的精确含义（不往 `README.md` 其他小节堆砌复述规格的废话）。

## 输出规范

本阶段审查报告按四部分输出：

1. **工具检查结果**：`ssot check` 与 `review.py` 的实际运行输出摘要及形式统计（规格行 / 注释行 / 文字行 / 图表行）。
2. **未定证明义务核验表**：列出每条 `未定` 证明义务的位置、要求条件、以及成立依据或缺失的前置条件。
3. **谓词严密性问题**：列出伪装重言式、说明承诺未落入谓词、或 `ext wr` 漏写保持条件的具体位置与修法。
4. **字面误读用词清单**：列出所有会把读者引向实例/缓存/存储的标识符与句子、出处行号、容易引发的误解，以及“改名”或“补说明注释”的具体方案。

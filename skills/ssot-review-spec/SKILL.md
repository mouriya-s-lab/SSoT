# ssot-review-spec：审形式化规格严密性、证明义务与用词对齐

开始前先读 `ssot`。按以下四步核验形式化谓词、说明注释与命名是否准确严密：

---

## 第一步：运行 `ssot check` 与 `jev` 模型审查

1. 运行确定性检查与 QuickCheck 反例搜索：
   ```sh
   ssot check <design>
   ```
   确认 8 个阶段（`layout`、`parse`、`structure`、`antipattern`、`form`、`prose`、`typecheck`、`quickcheck`）全部通过，退出码为 0，无 Warning。记下输出末尾的正文形式统计（规格行、说明注释行、文字行、图与文法行）及列出的全部 `未定` / `未评估` 证明义务。
2. 在 omp 的 Python `eval` 中运行 `jev` 语义反模式审查：
   ```python
   %load skill://ssot/scripts/review.py
   findings = await review("/path/to/repo/design")
   ```
   确认 12 类语义反模式检出数为 0；若有检出，按输出的 `文件:行号` 与反模式类别逐条列入待修项。

---

## 第二步：顺着上下文守卫核对「未定证明义务」

**怎么想：**
`ssot check` 通过只代表 QuickCheck 没有撞出反例；对输出中列出的每一条 `未定`（MAYBE）或 `未评估`（UNCHECKED）证明义务，回到源码那一行，问：**VDMJ 担心这里发生什么越界或类型不符？往上看两行（或看模块不变式），有没有条件已经把这个担心排除了？**

| 证明义务位置与种类 | VDMJ 要求成立的条件 | 上下文中的守卫或不变式（`文件:行号`） | 是否成立 |
|---|---|---|---|
| 例：`architecture/run.md:79:44` (`Recover`: subtype obligation) | `Finish(found)` 要求 `found` 的类型是 `RunId`（不能是 `<Absent>`） | 第 79 行 `if found <> <Absent> then Finish(found)`，且 `StatusOutcome = RunId \| <Absent>` | **成立**（`if` 分支已排除 `<Absent>`） |
| 例：`architecture/attempt/attempt.md:27:6` (`Unresolved`: sequence apply obligation) | 访问 `log(i)` 要求 `i in set inds log` | 第 27 行集合推导式绑定 `i in set inds log` | **成立**（绑定域已保证） |

- 如果往上看遍了前置条件 `pre`、状态不变式 `inv` 和所在分支的 `if`/`cases` 条件，都找不到能保证它成立的守卫（例如直接访问映射 `m(k)` 却既没有 `pre k in set dom m` 也没有分支判断 `k in set dom m`），那就是**真正漏写了前置条件或分支守卫**。

---

## 第三步：核对「说明注释 $\leftrightarrow$ 签名/字段 $\leftrightarrow$ 谓词」三者合一

**怎么想：**
工具检查看的是语法形状，人（和审查 Agent）看的是**诚实度**：逐个定义把它的 `--` 说明注释、参数/字段签名、以及 `inv`/`pre`/`post` 摆在一起，问：**说明里吹的牛，底下签名和谓词兑现了吗？**

重点核查四类脱节：
1. **说明与签名/字段对不上：**
   - `--` 说明里写“携带某某载荷”“接收某某参数”“区分 A 与 B 两种结局”，结果往下一看，记录里根本没有那个字段、函数参数表里没有那个参数、或者只放了一个 `bool` 字段把说明里要区分的几种结局混成了一团。
2. **说明里的承诺没写进 `inv`/`pre`/`post`：**
   - 说明里写了“同一请求号只产生一次运行”“已关闭时必拒绝”“保持一致”，看底下的 `inv`/`pre`/`post` 有没有对应的合取项把违规情形真正排除掉（注：跨操作的调用先后次序由编排场景规定，不要求在单个被调操作的 `post` 里重复设防）。
3. **用恒真子句假装使用了参数：**
   - 为了消除 VDMJ 的“参数未使用”警告，在 `post` 里塞进形如 `and (x = {} or x <> {})` 的废话，形式上挂住了参数名，实际上什么也没约束。
4. **隐式操作漏写状态保持条件（Frame Condition）或伪装纯函数：**
   - 隐式操作声明了 `ext wr x wr y`，在某个 `or` 分支（尤其是失败或幂等分支）中如果只写了 `x = x~` 而漏写 `y = y~`，VDM-SL 的语义就是允许该分支把 `y` 改成任意值！必须逐分支核对所有未变 `wr` 分量的 `= ~` 是否齐全（例如 `Run`Start` 的 `<Rejected>` 分支完整写出 `byRequest = byRequest~ and live = live~`）。
   - 检查是否有不读写任何 `state`（无 `ext rd/wr`）却写成隐式 `operations` 的定义——不涉及状态的操作应当写成纯函数 `functions`。

---

## 第四步：核对「字面用词 $\leftrightarrow$ 函数与值定义」是否一致

**怎么想：**
最后通读一遍规格里的标识符、`--` 说明注释与 `README.md` 正文，站在一个初次读这份文档的读者角度问：**如果我只按中英文字面意思理解这个词，我会不会把本系统的“纯函数、不可变值与源头事实”误解成别的机制？**

| 排查方向 | 容易引发误解的字面用词 | 读者按字面会误解成什么 | 怎样在持有处对齐修正 |
|---|---|---|---|
| **实例与指针词** | “实例”“对象”“成员变量”“指向某个实例”“重附着到实例” | 以为存在有可变状态、有内存地址的面向对象实例 | 改用函数、值、静态定义、不可变事实记录与凭据的表述 |
| **动作与状态词偏离实际定义** | 实际定义是“按等价关系引用已发布事实”，字面却叫“拷贝/复用环境”；或实际定义是“输入变了构成新调用”，字面却叫“原地重跑同一调用” | 以为从旧执行实例里搬走了状态，或把同一次函数调用跑了两遍 | 在持有该元素的模块改名（并同步更新全部 `imports` 与双反引号引用），或在该定义处的 `--` 说明注释中直接写明它在函数与值模型中的精确定义 |
| **存储与实现理由词** | 在「为什么」或注释里写“不存储结构副本”“避免存储同步负担”“不作为可变字段存储” | 以为是在讨论数据库表设计或内存字段优化 | 改写为设计层面的真实理由（单一展开避免多重解释、源头事实上的纯函数投影） |

---

## 本阶段输出

完成以上四步后，输出阶段三审查结论：

1. **工具检查与形式统计**：`ssot check` 与 `review.py` 的运行结果及规格/注释/文字/图表行数占比。
2. **未定证明义务核验表**：每条 `未定` 证明义务的位置、要求条件及上下文守卫（或缺失的守卫）。
3. **说明—签名—谓词脱节清单**：列出说明与签名不符、承诺未入谓词、`ext wr` 分支漏写保持条件或无状态隐式操作的具体位置与修法（附 `文件:行号`）。
4. **用词对齐清单**：列出字面容易引发实例/缓存/存储误解的标识符与句子、出处行号，以及改名或补清 `--` 说明注释的具体方案。

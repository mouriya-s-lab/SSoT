# ssot-verify-behavior：评审一张接线图

判断方法见 `ssot-quint`「九、评审时怎么判」。`scope` 是 Quint 模块名 Q，被评的是 `behavior/<Q>.qnt`。契约盒子集 M：Q 在 `Call` 里调用的契约模块。视图集 V：M 中每个模块所属元素（模块名里的 `_` 换回 `.`）的父元素的视图。

| 项 | 内容 |
|---|---|
| 输入 | `scope`；本模块的组合图路径；设计目录路径；对 V 中每个视图运行 `ssot check <design> --scope <视图>` 的诊断 |
| 可读 | 组合图；`behavior/<Q>.qnt` 与它 import 的非生成行为模块；`.gen/contract.qnt`；M 中每个模块的导出签名与导出端口的 `pre`/`post`；M 所属元素在 `structure/*.c4` 里的描述与关系；本模块附着的需求编号在 `requirements.md` 里的原文；交给你的诊断 |
| 可改 | 无 |
| 可运行 | 没给诊断时，对 V 中每个视图运行 `ssot check <design> --scope <视图>` |
| 输出 | 发现（见「交付」） |
| 上抛 | 问题的根源在契约（缺端口、缺结局、`post` 与担心不符）或结构（缺关系、职责放错元素）时，在发现里写明它属于哪个元素的 `ssot-write-contract`，或哪个视图的 `ssot-write-level` |

## 派发

会话运行 `ssot render <design>` 与每个 `check --scope`，按 `ssot` 第九节派一个新的 `ssot:reviewer`，交给它本 skill 名、`scope`、组合图路径、设计目录路径与诊断。原样交付它的发现。下面各节写给评审者。

## 一、先只看组合图

不读模块，先看图：有哪些步骤盒子、哪些线（行为一侧的 `var`，圆角标签，标出类型）、哪些契约盒子（另一种样式）；每个步骤从哪些线取、往哪些线放、又读又改哪些线、调用了哪个契约端口（`ssot-quint`「七」）。问：盒子与线是不是模块开头写的担心需要的那些；顺接的步骤是不是画成“线 → 步骤 → 线 → 步骤”的一串；有没有一条线被很多步骤又读又改（它在记进度）；连着几乎所有线的是不是只有崩溃这类环境与停机接管这类收束。图上读不懂的记为问题。

## 二、再看整体

读模块开头写的担心，回答：它要求哪些跨盒子的先后与收束？参与者各是谁、各自知道什么？再对照模块：每个动作是哪个盒子的一步，`safety` 守的是哪条可观察的关系，`witness…` 覆盖的是哪些必须走到的情形。

## 三、清单

按 `ssot-quint`「九」逐项判断。其中“换掉一个盒子会怎样”一项，对每条性质写出一个会让它失败的错误盒子或错误接线；写不出时，这条性质记为问题。

`replay.outcome` 里计数为 0 的结局变体：先看调用方有没有接住它的后续处理；有处理但没走到，是缺覆盖目标或调度走不到；没有处理，是缺路径。计数为 0 不证明这个变体不会发生，不据此要求删契约的结局。`resource.deadline` 说明验证没做完：写进交付，不当作通过。

## 四、交付

只交付发现，一条一项：

- 清单项名；
- 位置：组合图上的盒子或线，或 `behavior/<Q>.qnt:<行>` 与声明名；
- 观察到的事实，以及它为什么构成问题；
- 应由哪个 skill、哪个 `scope` 修：本模块的问题是 `ssot-write-behavior` 与本 `scope`；契约的问题是对应元素的 `ssot-write-contract`；结构的问题是对应视图的 `ssot-write-level`；担心本身不成立是 `ssot-judge`。

每条 info 写出你的判断：是问题，还是不构成问题（写理由）。没有发现时写明“未发现问题”，并列出你核对过的性质与覆盖目标。不改文件。

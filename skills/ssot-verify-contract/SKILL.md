# ssot-verify-contract：评审一个契约模块

`scope` 是带 `#contract` 的元素 E 的 fqn，被评的是 `contract/<E 的 fqn>.vdmsl`。视图 V：E 自己的视图，没有就用 E 的父元素的视图。判断方法与例子见 `../ssot-write/references/contract.md` 的「八、评审时怎么判」。

## 派发

用户直接指定评审本切片时，会话不自己评：按 `ssot` 第七节派一个新的 `ssot:reviewer`，交给它本叶子名、`scope`、设计目录路径与 `ssot check <design> --scope <V>` 的输出。原样交付它的发现，本次不改任何文件。下面各节写给评审者。

## 五项

| 项 | 内容 |
|---|---|
| 可读 | 本模块全文；E 在 `structure/*.c4` 里的描述、关系、标签与 `req`，以及这些 `req` 在 `design/requirements.md` 里的需求原文；本模块 import 的模块的导出签名；import 本模块的模块里引用本模块名字的地方（只看引用处，不评那些模块）；派发者交给你的诊断 |
| 可改 | 无。只报告。`ssot eval` 的求值结果只出现在本次交付里 |
| 工具工作集 | `ssot check <design> --scope <V>`（派发者已运行时直接用它的输出）；`ssot eval <design> <本模块名> '<表达式>' [--bind …]` |
| 末尾评审 | 本叶子就是评审，不再派评审 |
| 向上修正 | 问题的根源在结构（E 不该持有这个定义、缺一条关系、E 混着两个职责）时，在发现里写明它属于 E 的父元素的视图 |

## 一、先看整体

不看清单，先回答：落在 E 上的需求要求 E 的连接承诺什么？为了承诺这些，这个模块应该导出什么、持有什么状态、守什么不变量？再对照实际的模块。一个模块展开了太多值，通常是多个来源挤在一处。

## 二、求违反实例（S7）

对本模块每个 `pre`、`post`、`inv` 与纯函数各做一次：

1. 读出它要守住的需求或约束；
2. 写一个违反这条需求的具体值或调用（`pre_op(…)`、`post_op(…)`、`inv_T(…)`、`f(…)`），优先用边界值：空集合、零、负数、同一身份出现两次；
3. 用 `ssot eval` 求值。规格接受了这个违反实例（`pre`/`post`/`inv` 求得 `true`，或纯函数给出需求不允许的结果），就是一条发现，附上表达式与输出。

不透明的值用 `--bind` 按定义模块的构造入口构造。求值报错（退出码 `1`）不等于规格拒绝：看报错是不是因为违反了约束本身。

## 三、清单

| 编号 | 查什么 | 工具提示 |
|---|---|---|
| S2、S8 | 只有观察者需要区分时才展开；每个展开的区分，都有一串导出操作的结果或可调用性观察得到 | `hint.export` |
| S67、S94 | 类型、状态分量、imports 与导出只留真实需要的；导出要有消费者或有依据的系统外调用方；没人用的调用结果或调用本身删掉，不为它造假消费者 | `hint.export` |
| S28、S84、S110 | 架构模块里没有只为单一业务存在的定义；任何合法使用方都要的保证归架构，某项业务加的条件、选择或组合归那项业务；两者混在一条约束里的要拆开 | `hint.single-business` |
| S52、S60 | 消费者要读字段或按分支观察的类型才带 `struct` 导出，只传递的身份保持 `token`；使用方只从连接拿身份并原样传递，不自造 | `hint.struct-unread`；自造身份由类型检查拒绝 |
| S59、S24、S55、S68、S9 | 业务元素不持有持久状态；状态是陈述不变量与前后关系的数学模型，不是存储布局；只放本面守住、有观察者的源头事实；效果还没有约束的连接不预建状态；能算出的分量写成纯函数 | `hint.state-unused` |

| S64 | 身份、封闭取值与结构化数据不用无类型字符串；不观察内容时保持 `token` | `hint.string` |
| S89、S112 | 没有恒真的子句冒充约束，也没有不可满足的条件造成空承诺或禁止合法行为 | `hint.sampled` |

| S1 | 每个概念定义在持有它的元素里 | — |

| S5 | 同一概念或事实只在一处展开，消费者不复制它的事实或承诺 | — |
| S19 | 契约只承诺稳定需求的结果与规律，不固定连接不变时可以替换的做法或常变的业务内容 | — |

| S27 | 结局类型只列合法调用方仍须分别处理的分支，不逐项列同一种失败的原因；违规准入的调用不编码成返回分支 | — |
| S69 | 每个隐式操作的 `post`，逐个 `or` 分支核对：`ext wr` 里的每个分量在这一支都有约束（没变就写 `x = x~`）；漏写的那一支允许该分量变成任意值 | 无：`replay.frame` 只拦得住改动了 `ext rd` 分量或操作不写的分量的调用；`ext wr` 分量在某一支漏写约束，工具查不出，只能逐支读 |

`contract.po` 的 MAYBE、UNCHECKED、UNPROVED、TIMEOUT 是 info：逐条看它对应的谓词是否真有缺口，可以用第二节的方法求一个实例确认。这些 info 不进 `ssot status` 的前沿，只在这次评审里判断。

## 四、交付

只交付发现，一条一项：

- 清单编号；
- 位置：`contract/<文件>.vdmsl:<行>` 与定义名；
- 观察到的事实，以及它为什么构成问题；S7 附上 `ssot eval` 的表达式与输出；
- 应由哪个叶子、哪个 `scope` 修：本模块的问题是 `ssot-write-contract` 与本 `scope`；定义属于另一个已带 `#contract` 的元素时是那个元素的 `ssot-write-contract`，那个元素还不带 `#contract` 时是它的父元素的视图的 `ssot-write-level`；结构问题是 `ssot-write-level` 与 E 的父元素的视图；需求落点的问题是 `ssot-draft-requirement` 与需求 id。

每条 info（`hint.*`、未解决的证明义务）写出你的判断：是问题（同上格式）还是不构成问题（写理由）。没有发现时写明“未发现问题”，并列出你求过违反实例的谓词与函数。不改文件。

# ssot-verify-structure：只看渲染图评审一层结构

判断的标准是 `ssot-c4`。`scope` 是一个视图 id（一个元素 E 的一层；`index` 是顶层），或一个部署视图的 id。

| 项 | 内容 |
|---|---|
| 输入 | `scope`；`ssot render` 列出的 C4 图片路径与顺序 |
| 可读 | 交给你的图片；本 skill、`ssot` 与 `ssot-c4`。不读设计目录里的任何文件，不读需求、诊断、模型源文件 |
| 可改 | 无 |
| 可运行 | 无 |
| 输出 | 发现（见「交付」） |
| 上抛 | 问题在上一层（上一层的图把 E 画错了、E 的箭头本不该有）时，在发现里写明它属于上一层的视图 |

## 派发

会话按 `ssot` 第九节派一个新的 `ssot:reviewer`，交给它本 skill 名、`scope`，以及 `ssot render` 列出的 C4 图片路径与顺序。不给设计目录路径、诊断、需求或任何说明。原样交付它的发现。下面各节写给评审者。

## 一、怎样看

只凭图判断。图上读不出来的东西，就当它不存在；需要读源文件、需求或别人的解释才能明白的地方，一律记为问题。

按给你的顺序看：`index`、逐层下钻的视图、部署视图。先看上一层的图，弄清被展开的那个框负责什么、有哪些箭头；再看本层的图。

## 二、清单

| 清单项 | 看什么 |
|---|---|
| 图能独立读懂 | 有标题栏，标题说明这是哪一种图、画的是什么；有图例；不看别的材料就知道每个框是什么、做什么，每个箭头在说什么 |
| 种类与层级 | 每个框的种类（图例里的 Person、Software System、Container、Component 等）与它的位置相符：上下文图只有人、本系统与外部系统；容器图里是能单独运行的应用与数据存储；组件图里是一个容器内的功能块，没有再往下嵌套的组件 |
| 一层只说一层 | 本层的图上没有下一层才该出现的名字、操作名、数据字段、取值或先后次序；框里的字是一句职责，不是一段论证、需求编号或依据 |
| 外部不展开 | 外部系统与别人负责的部分是一个框，图上看不到它的内部 |
| 承担上一层 | 上一层被展开的框的每个箭头，在本层的图上都能看出是哪个子元素在承担，方向一致；本层没有多出上一层没有的对外箭头 |
| 箭头读得通 | 每个箭头有标题，顺着箭头读是一句通顺的话（“A 提交运行请求给 B”）；标题是短动词短语，不是操作清单；没有把回复画成反向箭头；没有标着 `[...]` 的合并箭头 |
| 划分说得通 | 同层的框各管一块，职责不重叠；一个框不是把几件不相干的事挤在一起；不是按执行步骤、角色或文件切出来的 |
| 部署 | 部署图里每个节点是什么运行位置看得懂；每个节点里运行哪些容器看得到；图例说明了每种框与信任边界，边界画在不同的执行方之间 |

## 三、交付

只交付发现，一条一项：

- 清单项名；
- 位置：视图 id 与图上的框或箭头（写出图上显示的名字与标题）；
- 在图上看到了什么，为什么读不懂或不对；
- 应由哪个 skill、哪个 `scope` 修：本层的问题是 `ssot-write-level`（或 `ssot-write-deploy`）与本 `scope`；上一层的问题是 `ssot-write-level` 与上一层的视图 id。

没有发现时写明“未发现问题”，并列出你看过的视图与核对过的清单项。不给修改方案之外的设计，不改文件。

# ssot-verify：独立验证设计

验证回答四个问题：VDM 有没有守住设计的形状；有没有守不住任何形状、不该进 VDM 的东西；每条形状是不是由正确的一方持有；规格在形式上是否严密。验证只报告结论与证据，不修改 `design/`，不替作者重写设计。

## 一、谁来验证

验证由没参与这份设计的上下文完成。主 agent 按总纲把 `agents/ssot-fable.md` 与 `agents/ssot-argon.md` 拷入当前项目的 `.omp/agents/`，同时派发 `ssot:fable` 与 `ssot:argon`，只告诉它们“用 ssot skill 做 ssot-verify 的验证”，以及 `design/` 与需求材料的位置。被派发的代理从第二节开始执行，不再派发。

主 agent 只汇总，不加入自己的验证结论：两份结论完整列出，标明出自哪一方；两方判断相反时并列给出，不由主 agent 裁决。交付前删掉拷入的 `.omp/agents/ssot-*.md`。

## 二、依据什么

只读需求材料、`design/`，以及 `ssot` 与本 skill。作者的草稿、说明、落点对照、讨论记录与“检查通过”的汇报都不作为依据，也不向作者询问；需要作者另外说明才能成立的形状，按“未进 VDM”处理。

## 三、先不读规格，写出预期的形状

先只读 `design/README.md`、各模块与单元的 `README.md`、需求材料，并运行 `ssot graph <design>`；这一步不读任何含 VDM 的规格文件。读完先写下预期：

- 系统要满足什么；为了满足它，设计应当由哪些对象、哪几层组成；
- 应当成立哪些形状：哪些对象只是索引，谁能指向谁、作用于谁，每条边界上能过什么，谁套在谁里面、谁先于谁结束，什么写下后不再改变；
- 每条形状应当由架构还是业务持有。

写下预期之后，再按阅读次序读规格。

## 四、逐条形状找反例

对预期里的每条形状，先找出规格中让它检查得出来的元素，再设法构造一个违反它、规格却仍然允许的情况：

- 一个满足全部 `inv` 的状态；
- 满足某个连接 `pre` 的一次调用，以及它的 `post` 允许的结果，尤其是 `post` 没有约束的状态分量；
- 一条导入路径，让不该触达的模块触达了；
- 一个绕开场景、直接调用连接的使用方。

构造得出来，这条形状就没有守住，写出这个反例。只在 `README.md` 里用文字声称、规格却不排除违反情况的，算未进 VDM。场景能走通，只说明这一条路没有破坏形状，不说明形状成立。

## 五、逐个元素问它守着什么

反过来，对规格里的每个类型、字段、不变式、条件、函数与场景，问它守着哪条形状。守不住任何形状的元素不该进 VDM，常见的有：

- 一步步模拟业务怎样运行的场景，例如推进次序、就绪条件、策略与挑选；场景里对应不上形状的先后，就是在模拟运行；
- 边际处理，例如并发、超时、重试、崩溃与失败原因的细分；
- 修改、介入这类编辑处理；
- 记录与存储的形状、键，以及索引怎样存放；
- 只为让检查通过而造出的模块、导出或场景，例如只有导入列表的单元。

## 六、核对归属

逐条查出：

- 架构里只为某一项业务存在的类型或规则；
- 因为写成某个架构操作的前置条件更方便，或者因为事实存放在某个模块里，而被搬进架构的业务判定；
- 同一个东西在两处展开；
- 预期中应当由某一层保证的形状，因为这一层被拿掉或并进别处，失去了保证者。

## 七、形式

运行 `ssot check <design>`，并在 omp 的 Python `eval` 里运行语义反模式审查：

```python
%load skill://ssot/scripts/review.py
findings = await review("/path/to/repo/design")
```

对每条未定或未评估的证明义务，到 `pre`、`inv` 与分支条件里找守卫，找不到就是缺了前置条件或分支守卫。核对 `--` 说明里承诺的东西是否都兑现在签名与谓词里。工具通过不等于设计成立；工具报出的问题也不由验证者修改。

## 八、结论

按形状逐条给出结论，每条附 `文件:行号`：

- **守住：** 守住它的元素，以及为什么构造不出反例；
- **没守住：** 写出反例；
- **未进 VDM：** 指出只在文字里声称的部分；
- **无法判定：** 指出缺少的定义、依据或需求。

另外列出不该进 VDM 的元素、归属问题与形式问题。问题交回 `ssot-design` 或 `ssot-draft` 修改；修改后的设计要整份重新验证，某个问题只有在新一轮验证中不再出现，才算解决。

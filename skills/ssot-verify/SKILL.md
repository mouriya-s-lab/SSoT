# ssot-verify：独立验证设计

验证只报告结论与证据，不修改 `design/`，也不替作者重写设计。

## 一、谁来验证

主 agent 按总纲把 `agents/ssot-fable.md` 与 `agents/ssot-argon.md` 拷入当前项目的 `.omp/agents/`，同时派发 `ssot:fable` 与 `ssot:argon`。派发时只告诉它们“用 ssot skill 做 ssot-verify 的验证”，以及 `design/` 与需求材料的位置。被派发的代理从第二节开始执行，不再派发。

主 agent 只汇总，不加自己的结论：两份结论完整列出，标明出自哪一方；两方判断相反时并列，不裁决。交付前删掉拷入的 `.omp/agents/ssot-*.md`。

## 二、依据

只用需求材料、`design/`、`ssot` 与本 skill。作者的草稿、推理、落点表与“检查通过”的汇报都不作依据，也不向作者询问。一条约束要靠作者另外解释才成立，按“不成立”处理。

## 三、第一步：不看规格，写出应有的约束

先只读需求材料、`design/README.md` 与各模块、单元的 `README.md`，并运行 `ssot graph <design>`，不读任何含 VDM 的文件。读完写下应有的约束，每条包括：约束哪个对象、允许什么变化、什么关系不变、一个违反情形、应由架构还是哪个业务持有。

写对象时分清定义、执行、事实与索引：两份内容相同的它算一个还是两个，答案不同就是不同的对象。

写下之后再读规格，读完对照第一步，判出三种问题：

- **遗漏：** 需求要求的约束，规格里没有；
- **过强：** 规格写了需求没要求的更强约束，例如把本应独立的多次执行当成同一个；
- **误当必需：** 规格把怎样运行写成了约束。判定方法：换一种实现或调用先后，需求仍然满足，规格却不再满足。

## 四、第二步：逐条找违反情形

对每条应有的约束，先找出规格里排除违反情形的类型或谓词，再试着构造一个规格允许、却违反这条约束的情况。依次试：

- 一个初始状态；
- 一次满足 `pre` 的调用，以及它的 `post` 允许的一个结果，尤其看 `post` 没约束到的分量；没列进 `ext wr` 的分量必须保持不变；
- 两个连接先后组合出来的状态；
- 不经场景、直接调用连接的使用方；
- 一条导入路径，让不该触达的模块触达了。

能构造出来，这条约束就不成立，把构造出的情况写成反例。场景能走通，只说明那一条路没有违反，不说明约束成立。

构造出的情况用 VDMJ 求值核对，`-default` 设成被验证的模块：

```sh
ssot vdmj <design> -default <模块> -e '<表达式>'
```

规格自动带有这几种函数：类型的 `inv_T(值)`；有前置条件的操作 `pre_Op(参数…, 状态)`；有后置条件的操作 `post_Op(参数…, 结果, 旧状态, 新状态)`，无返回值的操作没有结果这一项。`post_Op` 返回 `true`，就说明规格允许这次变化。`post_Op` 不检查 `ext`，框架要自己核对。`mk_` 构造状态时会检查 `inv`，违反 `inv` 的状态构造不出来。

## 五、第三步：逐个元素反查

反过来，对规格里的每个类型、字段、函数、操作与场景，问它守着第一步里的哪条约束，或者它是哪条约束所需的连接。答不出的，列为不该进 VDM 的元素。场景体里对应不上任何约束的先后、分支与挑选，是在模拟业务怎样运行，同样列出。

## 六、第四步：核对归属

对每条约束问：连接的提供方无论服务哪个合法使用方都必须保证它吗？还是某项业务在连接之上加的条件、选择或组合？按答案核对它实际写在哪里，列出：

- 写在架构里、却只为某一项业务存在的约束；
- 因为写成 `pre` 更方便、事实存放在架构里、业务没有 `state` 或架构不能导入业务，而被放进架构的业务判定；
- 同一个东西在两处展开。

## 七、第五步：工具

运行 `ssot check <design>`，并在 omp 的 Python `eval` 里运行语义反模式审查：

```python
%load skill://ssot/scripts/review.py
findings = await review("/path/to/repo/design")
```

对每条未定或未评估的证明义务，到 `pre`、`inv` 与分支条件里找守卫，找不到就是缺了前置条件或分支守卫。工具通过不代表约束成立；工具报出的问题也不由验证者修改。

## 八、结论

每条约束给出三种结论之一，附 `文件:行号`：

- **成立：** 排除违反情形的元素，以及为什么构造不出反例；
- **不成立：** 反例，或者规格内部的矛盾；
- **未能判定：** 缺少的定义、依据或需求。

另外列出第三步的遗漏、过强与误当必需，第五步不该进 VDM 的元素，第六步的归属问题，以及第七步的工具问题。问题交回 `ssot-design` 或 `ssot-draft` 修改。修改后的设计要整份重新验证；某个问题只有在新一轮验证中不再出现，才算解决。

# 结构的写法（LikeC4）

`ssot-write-level` 与 `ssot-write-deploy` 照这里写 `design/structure/*.c4`，`ssot-verify-structure` 照这里判断。例子取自 soroi 示例设计：使用方 `caller`，系统 `soroi`（含 `engine`、`store`、`workspace`），外部执行方 `preset`。

## 一、结构只写层级关系

结构持有这几类事实，别的载体不写：

- 元素与嵌套：系统由什么组成，谁在谁里面（抽象层级，父粗子细）；
- 依赖方向：谁依赖谁，以及这条依赖承担什么职责；
- 部署与信任边界：元素部署在哪个节点，节点之间的信任关系；
- 依据与理由：每个改变结构形状的决定依据哪条外部事实，为什么这样分；
- 需求落点：哪个元素承接哪条需求（`req`）。

下面这些不进结构，各有持有者：

| 不写进结构 | 持有者 |
|---|---|
| 操作名、类型名、状态字段、数据内容、取值 | 契约（VDM，见 [`contract.md`](contract.md)） |
| 先后、交错、窗口、超时、重试、崩溃后的接管次序 | 行为（Quint，见 [`behavior.md`](behavior.md)） |

关系标题只写依赖的职责，不写操作清单：`caller -[calls]-> soroi.store '取得运行事实'`，不写 `'replay、timeline、compare'`。描述写元素负责什么，不写它怎样一步步做：`'负责运行的停机：收束准入与全部未结束的运行项，写下运行的结束锚点'` 说的是职责；“先停准入、再逐个关闭闭包、最后写锚点”是次序，归行为。

## 二、元素种类与嵌套

`specification` 里只声明四种元素：

| 种类 | 粗细 | 位置 |
|---|---|---|
| `actor` | — | 只在顶层，没有子元素；系统之外的使用方 |
| `system` | 1 | 任意 |
| `container` | 2 | 任意 |
| `component` | 3 | 任意 |

子元素必须比父元素细；`component` 可以嵌套 `component`。

**什么时候展开出子元素。** 一组元素对外陈述连接、内部决定可以对其他元素隐藏、父元素不需要知道它的内部时，才拆成子元素。按抽象划分，不按篇幅、执行步骤或代码目录切；并列的兄弟彼此正交。

一个架构元素的三部分都在结构里有位置：它对外的关系是**外部连接**；它带 `#contract` 时，契约模块是连接点与它要守住的事实，即**核心**；它的子元素与子元素之间的关系是**内部设计**。业务元素不要求分这三部分。

**隐含前提。** 软件依赖、又不归本系统实现的东西（外部执行方、外部存储），写成系统之外的元素并画出依赖；它在本系统里实现时，就是本系统的某个元素。不属于软件的运行前提（供电、网络存在）不写。

## 三、关系

`specification` 里只声明三种关系；箭头方向就是依赖方向，源依赖目标：

| 种类 | 含义 | 授予契约引用 |
|---|---|---|
| `calls` | 运行期调用目标 | 是 |
| `uses` | 只用目标的契约词汇，没有运行期交互 | 是 |
| `callback` | 运行期回调一个依赖自己的元素 | 否 |

- **授予引用。** 元素 E 的契约模块只能 import：E 恰为源、T 恰为目标的 `calls`/`uses` 关系所指向的 `#contract` 元素 T 的模块，以及带 `#shared` 的祖先的模块。不扩张到 T 的后代，不继承祖先的依赖。所以契约要用谁的词汇，结构里就要有一条从它出发、恰好指向那个元素的关系。
- **反向调用用 `callback`。** 执行方交回结果、插槽回调核心这类“被依赖方运行期调回来”的情形，写 `callback`，它不形成依赖：`soroi.workspace.route -[callback]-> soroi.engine.closure '把执行方的交回与请求交给所属运行项的闭包过程'`。
- **架构不引用业务。** 带 `#business` 的元素及其后代是业务元素，其余（除 `actor`）是架构元素。架构元素不得有指向业务元素的 `calls` 或 `uses`。
- **无环。** 除 `callback` 外，每条关系提升到两端最近公共祖先之下的那一对兄弟；每个父元素之下（以及顶层），兄弟之间的依赖无环。
- **共用材料放在共同父元素。** 多个后代共用的身份与值边界，放在它们共同的父元素上，标 `#contract #shared`：`soroi` 持有 `RunId`、`RuntimeId` 与唯一的值解析边界，全部后代都能引用。

## 四、标签与 id

| 标签 | 含义 | 约束 |
|---|---|---|
| `#contract` | 该元素承载一个契约模块 | 必须有 `design/contract/<fqn>.vdmsl` |
| `#shared` | 该元素的模块可被全部后代 import | 同时带 `#contract`，且有子元素 |
| `#business` | 该元素及其后代是业务元素 | 不重复标在业务元素的后代上 |

信任边界等其他标签可以自由声明（示例用 `#implementer`、`#untrusted`）。标签名、元素种类、关系种类、metadata 的键与值都不得等于任何 VDM 定义名或 Quint 声明名。

承载契约的元素及其全部祖先，id 只用字母和数字（`[A-Za-z][A-Za-z0-9]*`）：模块名由 fqn 把 `.` 换成 `_` 得到（`soroi.engine.closure` → `soroi_engine_closure`）。

## 五、逐层声明关系与落实

一次写作只写一个元素 E 的一层：E 的直接子元素、这些子元素之间以及它们与外部元素之间的关系、E 的视图。

**关系声明在本层的兄弟之间。** 写顶层时，关系连在顶层元素之间；写 E 的一层时，关系的一端是 E 的某个直接子元素，另一端是它的兄弟，或 E 在上一层就有关系的外部元素。不要只在最深一层声明关系、让 LikeC4 派生上层的汇总边：派生边不算声明，上一层就没有需要落实的关系，删掉一条下层关系时评审包里只是少一行，没有任何“应有”的参照。

**展开 E 时，E 在上一层的每条声明关系都要在本层落实。** E 在上一层的对外关系，是一端恰好是 E 本身、另一端 X 在 E 之外的声明关系。落实它的是 E 的直接子元素 c：存在一条种类相同、方向相同的声明关系，一端是 c 或 c 的后代，另一端是 X 或 X 的后代。示例里同一串依赖逐层落下：

```text
// 顶层
caller -[calls]-> soroi '管理运行并取得运行事实'
// soroi 一层：落实 caller→soroi
caller -[calls]-> soroi.engine '管理运行的生命周期'
caller -[calls]-> soroi.store '取得运行事实'
// engine 一层：落实 caller→engine
caller -[calls]-> soroi.engine.control '管理运行的生命周期'
```

跨两个展开元素的依赖，两边各落实一次：soroi 一层声明 `engine → workspace`；engine 一层由 `closure → workspace` 落实它；workspace 一层再由 `closure → workspace.executor` 落实 `closure → workspace`。

**落实不了时。** 上一层的某条关系在本层找不到落实者，只有两种情况：本层漏了一条子元素关系，补上；或者上一层的划分本身不对（这条依赖不该存在，或者该指向别的元素），这时停下本层，回去重开父元素的那一层，不在本层另造一个子元素去凑落实。

## 六、视图

- 顶层恰有一个视图，id 为 `index`，没有 `of`，只含顶层元素。
- 每个有子元素的元素恰有一个 `view <id> of <fqn>`，通常 `include *`。计算出的节点只能是该元素、它的直接子元素，以及与这些子元素（含后代）有关系的外部元素；不得出现孙辈。
- 没有子元素的元素不建 `view of`。部署视图不受这几条约束。

```text
view engineView of soroi.engine {
  title 'Engine 内部'
  include *
}
```

视图 id 就是一层的名字：`ssot check <design> --scope engineView` 只报告这一层的诊断，`ssot view <design> engineView` 输出这一层的评审包。

## 七、部署与信任边界

部署节点种类在 `specification` 里用 `deploymentNode` 声明，节点里用 `instanceOf` 放元素。信任边界用节点上的标签与描述表达：

```text
host execEnv 'execution environment' {
  #implementer
  description '执行边界及其中的执行方；与 daemon 分属不同的信任边界'
  instanceOf soroi.workspace
  instanceOf preset
}
```

节点描述写部署事实（这个进程可以退出与重启、它与谁分属不同信任边界）；重启之后谁按什么次序接管、重新附着得到什么，是行为与契约的事实，不写在节点上。

## 八、依据、理由与需求

**依据**写外部世界改变不了的事实、约束、系统级需求与质量要求，每条写出来源，并说明它让结构多了或少了什么（“所以……”）。质量要求写成“在〈环境〉下，〈刺激〉发生时，〈响应〉满足〈度量〉”，数值只在有出处时写。当前实现的目录、调用步骤、偶然行为与技术选型不是依据。

**理由**：每个改变结构形状的决定都写理由并引用依据——拆出子元素、一条依赖的存在与方向、业务与架构的分界、一条信任边界。存在可信替代时，写一句为什么不选它。例如使用方直接从事实源头读取、不经过引擎，理由是读取运行事实不需要引擎协调。

依据与理由写进元素或关系的 `description`：评审包只带标题与描述，`//` 注释不进模型，评审者看不到。

**需求落点。** 需求 id 写进承接它的元素的 metadata，键为 `req`：

```text
control = component 'Control' {
  #contract
  description '使用方与引擎之间唯一的操作面：受理对运行生命周期的请求并分派'
  metadata {
    req 'R8'
  }
}
```

一个元素承接多条需求时写成列表 `req ['R8', 'R40']`。`ssot status` 只报告哪些需求 id 没有落点；有落点不等于已兑现，兑现与否由评审判断。需求本身的论证、领域性质和拆分由 `ssot-draft-requirement` 写，结构只记落点。`req` 指向的每条需求都要有真实来源，并写成问题域里可以被观察到的结果（使用方或外部系统看到什么），不是机器的功能清单；结构不为一条功能清单式的“需求”造元素。

两条不能用结构去补的情形：

- 不属于本系统承诺的需求，不为兑现它而扩张结构（加元素、加依赖）；把它退回需求论证。
- 业务判定缺少所需事实时，改连接要提供的内容（契约导出什么），不把判定搬进架构元素。

## 九、工具会拒绝什么

`ssot check` 把下面这些当错误，check 失败：

| 规则 | 拒绝什么 |
|---|---|
| `compile.c4` | LikeC4 语法与引用错误 |
| `struct.kinds` | 第二、三节之外的元素种类或关系种类 |
| `struct.nesting` | 子元素不比父元素细；`actor` 不在顶层或有子元素 |
| `struct.layering` | 架构元素以 `calls`/`uses` 指向业务元素；`#business` 重复标记 |
| `struct.acyclic` | 某个父元素之下兄弟依赖成环 |
| `struct.views` | 第六节的视图要求 |
| `struct.ids` | 承载契约的元素或其祖先的 id 含字母数字以外的字符 |
| `vocab.slots` | 种类、标签、metadata 的键或值等于契约或行为里的名字 |
| `contract.module` | `#contract` 与契约文件、模块名不一一对应；`#shared` 没有同时带 `#contract` 或没有子元素 |
| `contract.imports` | 契约 import 越出第三节的授予范围 |
| `gen.fresh` | `.gen/structure.json` 与重新生成的结果不一致（它只由 `ssot gen` 写出，不手改） |

只作提示、不拒绝的：`view.unrealized`（上一层的关系在本层没有落实者）、`ssot status` 报出的没有落点的 `req`、`ssot check --base <rev>` 列出的作用域之外的改动。标题与描述等自由文本工具不扫描，全部交给评审。

## 十、评审时怎么判

结构评审一层一层看。先运行 `ssot view <design> <视图>` 得到本层评审包，再逐项判断：

1. **逐条核对落实。** 评审包列出被展开元素在上一层的每条对外关系与本层的落实者。对每一条问：落实者是不是真正承担这条职责的子元素，种类与方向对不对；“未落实”一栏的每一条，判定是本层漏了关系，还是上一层的划分错了。
2. **读汇总边的真实两端。** 上层视图里的一条边可能汇总了多条下层关系。判断一条边对不对，看评审包列出的真实两端与标题，不把汇总边当成两个上层元素之间的直接依赖：工作区内部的插槽启动 agent，在 preset 的视图里显示成 `soroi → agent`，那不是 `soroi` 自己依赖 agent。
3. **依据与理由。** 本层每个子元素、每条关系、每个 `#business` 与信任边界的划分，都有带来源的依据与理由；依据不是当前实现、调用步骤或技术选型；有可信替代的写了不选的理由。
4. **三部分。** 每个架构元素的外部连接、核心与内部设计分得清：对外关系只连它真正对外提供或依赖的东西，内部决定没有漏到外部关系上。
5. **需求关联。** 本层元素上的 `req` 指向的需求有真实来源、写成可观察的结果，并确实由这个元素承接；没有为兑现系统之外的承诺扩张结构；业务判定没有搬进架构元素。
6. **每个元素都服务需求。** 每个元素与每条关系都能指出它服务的需求或需求所需的连接；只为通过检查、为凑落实或为让名字有落点而造的元素与关系，删掉。
7. **禁止内容。** 标题与描述里没有操作名、类型名、状态字段、数据内容和先后次序。

评审只看本层与评审包，不保存“已确认”；发现上一层划分不对时，结论是重开父元素，而不是在本层修补。

# soroi 示例

`design/` 是一个处在某个阶段的 soroi 设计，用来演示 `ssot` 的方法，不是写满的模板。

**阶段（使用者声明）。** 容器划分已经稳定；闭包过程与停机已经落地运行，并有这几条运行观测：

1. daemon 崩溃过；崩溃前发出的 launch，在重启之后才被执行边界回复。
2. 崩溃恢复之后，同一个运行项的结束被写下过两次，也出现过运行项还没有结束、运行的停机锚点就已写下。
3. 一个实现者提供的执行边界，在闭包关闭之后仍接纳过晚到的 launch。

别的部分还没有运行观测。

**结构。** 上下文与容器两层是默认的导航图。Engine 画了组件层，因为上面的观测都落在 Engine 内部：读图的人要能看到闭包过程（Closure）与停机过程（Halting）是 Engine 里的哪两块、它们各自连着哪些容器（`structure/soroi.c4`）。

**往下写的位置只有两个盒子和一张接线图**，三问的回答与支撑精度的观测如下：

| 位置 | 具体的担心 | C4 与编译检查能否定位 | 模型会揭露的错误 | 支撑精度的观测 |
|---|---|---|---|---|
| 收束接线 `behavior/winddown.qnt` | 停机或崩溃之后，运行项的结束在闭包里还有执行时就被写下；已退出的 daemon 发出的 launch 在闭包关闭之后被接纳 | 不能：它取决于崩溃、停机与晚到回复之间的交错 | 执行边界在关闭之后仍接纳 launch，或停机不关闭闭包就写结束，都会让 `safety` 失败；崩溃落在停机写完结束、写锚点之前时，运行停在没有锚点的状态，覆盖目标 `witnessCrashBeforeAnchor` 走到它，`daemonLost` 接管 | 1、2 |
| 事实源头盒子 `contract/soroi.store.vdmsl` | 同一个运行项的结束写两次；停机锚点早于运行项的结束 | 不能：写入方有闭包过程与停机过程两处 | 接线里闭包过程与停机过程都去写同一个运行项的结束，或停机锚点写在结束之前时，回放按 `writeEnd`、`writeHalt` 的 `pre` 报错 | 2 |
| 执行边界盒子 `contract/soroi.workspace.vdmsl` | 关闭与在途 launch 的互斥（实现者注入的边界） | 不能：互斥发生在边界内部 | `launch` 的 `post` 不再要求关闭后拒绝时，收束接线的 `safety` 失败 | 3 |

两个盒子的精度只到这些性质：记录的内容、注入、取回的内容、现场、配置与失败分支都不展开；`open`、`collect` 只写接线要用到的最少前后关系。

**其余位置保持不可见。** Control、Scheduler、Derivation、Values 没有 `#contract`，也不出现在接线里：它们要么是标准范式，要么还没有运行观测。Closure 与 Halting 只作为接线里的步骤与停机过程出现，没有自己的盒子：它们的担心在接线上，不在某个端口的承诺上。`requirements.md` 里多数需求没有附着，这是正常的：它们由结构回答，或留给代码。

**渲染。** `ssot render design` 导出 C4 图、两张盒子图与收束接线的组合图。
